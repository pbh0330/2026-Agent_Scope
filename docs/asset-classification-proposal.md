# 자산 분류를 8종으로 확장하는 방안 — 팀 협의안

> 작성일: 2026-10-02
> 상태: 팀 의견 수렴용 제안

## 1. 제안

**수집·관리할 자산을 Gateway, Node, MCP Server, Tool, Resource/Template/Prompt, Skill, Plugin, Permission/Auth의 8종으로 확장하면 어떨까요?**

Gateway를 독립 자산으로 관리하면 어느 Gateway에 어떤 서버가 등록돼 있는지, 공통 설정이 어떤 자산에 적용되는지 연결해서 볼 수 있습니다. Permission/Auth도 함께 관리해 정책·인증 설정과 적용 대상을 추적하는 방향을 제안합니다.

MCP 공식 객체의 필드·구조와 OpenClaw 원천 설정 키를 보존하는 원칙은 유지합니다. 자산 ID·유형·관계는 프로젝트의 추가 정보로 구분합니다.

## 2. 제안하는 자산 8종

| 유형 코드 제안 | 자산 | 관리할 내용 |
|---|---|---|
| gateway | Gateway | Gateway 인스턴스, 설정, 서버 선언 정보 |
| node | Node | 분산 실행 노드의 식별·설정 정보 |
| mcp_server | MCP Server | 서버 선언·연결 설정과 발견 정보 |
| tool | Tool | 서버가 제공하는 개별 도구 정의 |
| resource_prompt | Resource / Template / Prompt | 리소스·리소스 템플릿·프롬프트 정의. 하위 유형으로 구분 |
| skill | Skill | 설치·선언 정보와 공급 출처 |
| plugin | Plugin | 설치·선언 정보, 공급 출처와 확장 관계 |
| permission_auth | Permission / Authentication | 식별 가능한 권한 정책 또는 인증 설정·참조. 하위 유형으로 구분 |

8종은 자산의 **분류 수**입니다. 실제 자산 개수는 환경에 따라 달라지며, 각 유형의 수집 지원 여부도 별도로 표시합니다.

## 3. 관계 표현 예시

다음은 구조를 설명하는 가상 예시입니다.

```text
Gateway A ── DECLARES ──▶ MCP Server B ── ADVERTISES ──▶ Tool C
Node D    ── DECLARES ──▶ MCP Server E

Permission/Auth P ── 적용 대상 참조 ──▶ MCP Server B
```

- `DECLARES`: 해당 Gateway 또는 Node의 설정에 서버가 등록돼 있다는 의미입니다. 실제 접속 성공과 구분합니다.
- `ADVERTISES`: 서버 목록에서 해당 도구가 제공됨을 확인했다는 의미입니다. 실제 실행 성공과 구분합니다.
- 적용 대상 참조: 정책·인증 설정이 어느 자산에 적용되는지 연결합니다. 구체적인 필드·관계 이름은 협의합니다.

이 구조를 사용하면 서버의 선언 위치와 도구의 소속, 적용 정책을 함께 확인할 수 있습니다.

## 4. 함께 정할 사항

### Gateway 식별과 서버 소속

Gateway는 환경 내 설치 인스턴스를 기준으로 식별하고, 반복 수집에서도 같은 ID를 유지하는 방향을 제안합니다. 실제로 사용할 원천 식별 정보는 테스트베드·스캐너 담당자가 확인합니다.

Server의 소속이 설정을 등록한 주체를 뜻하는지, 실제 실행 위치를 뜻하는지도 명확히 정해야 합니다. 원격 서버는 등록한 Gateway와 실행 위치가 다를 수 있습니다.

### Permission/Auth 집계 단위

독립적으로 식별 가능한 정책 또는 인증 설정을 한 건으로 관리하고, 적용 대상은 참조로 연결하는 방향을 제안합니다. 하나의 정책이 서버 세 개에 적용돼도 정책을 세 번 복제해 세지 않습니다.

인증 설정의 식별과 자격증명 공유 여부는 구분합니다. 같은 환경변수 이름만으로 동일한 자격증명이라고 판단하지 않으며, 실제 비밀값과 그 해시는 저장하지 않습니다.

### 수집 범위와 자산 수

전체 자산 수와 유형별 개수는 고유 자산 ID를 기준으로 집계합니다. 화면에서 Gateway를 그룹과 자산 노드로 함께 표현하더라도 중복 집계하지 않습니다.

정상 조회 결과 0건, 아직 지원하지 않는 유형, 조회 실패를 구분해 표시합니다. 8종 분류 채택과 각 유형의 수집 구현 일정은 별도로 협의합니다.

## 5. 채택 시 함께 반영할 범위

| 대상 | 반영할 내용 |
|---|---|
| 전체 공격표면 문서 | 8종 분류, Gateway·Node 역할, 권한·인증의 위치, 관계와 최소 수집 항목 |
| 공통 스키마 | 유형 코드, Gateway ID, 서버 소속·참조, 정책 적용 대상, 집계 규칙, 예제와 계약 버전 |
| 스캐너 | Gateway 식별·설정·근거 수집, 서버 선언 관계 생성, 유형별 지원·실패 상태 |
| 테스트베드·Ground Truth | 실제 자산과 관계의 정답 목록, 8종 집계, 식별 근거 제공 |
| 대시보드 | 8종 목록·필터·그래프·상세 화면, 유형별 집계와 중복 방지 |
| 위협 시나리오 | 관련 자산·정책 참조와 관계 예시 |
| QA | 자산·관계 ID 매핑, 수집률 기준, 중복 집계·미수집·실패 사례 검증 |
| 토큰·비용 | 환경·Gateway·서버별 도구를 자산 ID와 연결하는 방식 검토 |
| 계획서·개발 문서 | 분류·산출물·완료 기준과 적용 일정 |

공격표면의 A/B/C 분석 범위와 MCP·OpenClaw 원천 정의는 유지하며, 프로젝트의 분류·연결·집계 기준을 맞춥니다.

## 6. 팀에 요청할 의견

1. **위 8종을 공통 자산 분류로 사용하는 방향에 동의하시나요?**
2. Gateway 식별 정보와 서버 선언 관계를 어떤 원천에서 수집할 수 있을까요?
3. Permission/Auth를 한 건으로 구분하는 기준은 어떻게 잡으면 좋을까요?
4. 각 담당 영역에서 추가로 필요한 필드나 구현상 어려운 부분이 있을까요?
5. 합의된 내용을 각 파트에 반영 가능한 일정은 어느 정도일까요?

합의되면 공통 출력 예제를 먼저 작성해 스캐너·대시보드·QA가 자산과 관계를 동일하게 해석하는지 확인한 뒤, 관련 문서와 구현에 반영하고자 합니다.
공통 스키마와 관련 문서의 통합 정리는 제가 담당할 예정이며, 각 파트에서는 구현 가능 여부와 필요한 변경사항, 적용 일정을 확인해주시면 좋을 것 같습니다.
