# Agent Scope 공통 데이터 구조 협의안

> 작성일: 2026-09-29 · 상태: 협의 전 제안
> 목적: 각 파트가 데이터를 주고받기 위해 먼저 맞춰야 하는 최소 구조와 표현 규칙을 합의한다. 필드명·자료형·담당은 모두 제안이며, 결정 기록란에 합의 내용을 남긴 뒤 확정한다.

## 1. 이번 협의에서 정할 것

**각 파트의 세부 구현이 끝나기 전에, 같은 자산을 같은 ID로 식별하고 수집 결과를 같은 의미로 해석할 수 있도록 공통 구조를 맞춘다.**

| 이번에 합의할 항목 | 담당자 확인 후 구체화할 항목 |
|---|---|
| 모듈별 데이터 생성·전달 책임 | 실제 수집 가능한 자산별 상세 필드 |
| 환경·자산·스냅샷의 식별 방법 | 권한·공급망 정보의 수집 가능 범위 |
| 자산·관계·근거·수집 상태의 기본 구조 | 보안 점검 결과·이벤트의 생성 주체와 상세 내용 |
| 시각·미확인 값·빈 목록·오류 표현 | 사용량 관측 단위·추정 방법·비용 계산 기준 |
| 자산 데이터와 사용량 데이터를 연결하는 규칙 | API 경로·갱신 주기·화면별 조회 방식 |
| 예제 데이터 검토 및 변경 절차 | 저장 DB와 내부 테이블 구조 |

시나리오의 내용·번호·공격 단계는 이번 협의에서 정하지 않는다. 필요한 데이터 요구사항은 해당 담당자가 제공하는 자료를 바탕으로 후속 반영한다.

## 2. 데이터 흐름과 책임 제안

```text
테스트베드의 설정·자산 목록
          ↓
       스캐너 ── 자산 스냅샷 ──→ 보안 대시보드 / QA

실행 기록·사용량
          ↓
  사용량·비용 모니터링 ──→ 자체 비용 화면
          └── 사용량 데이터 + 자산 연결 정보 ──→ 보안 대시보드 / QA

보안 점검 결과·이벤트: 생성 모듈과 전달 경로를 담당자 협의로 결정
```

| 데이터 | 생성 책임 제안 | 소비 주체 | 먼저 확인할 내용 |
|---|---|---|---|
| 환경 식별 정보 | 테스트베드 담당이 기준 제공, 각 모듈이 공통 사용 | 전체 모듈 | 같은 환경을 가리키는 ID와 초기화·복제 시 변경 규칙 |
| 자산·관계·수집 근거 | 스캐너 | 보안 대시보드·QA·모니터링 연결 작업 | 안정적인 자산 ID 및 예제 출력 |
| 사용량·비용·귀속 결과 | 모니터링 | 자체 화면·보안 대시보드·QA | 관측 단위와 자산 연결 가능 여부 |
| 보안 점검 결과·이벤트 | 미정 | 보안 대시보드·QA | 누가 생성하고 어떤 근거·대상 ID를 제공하는지 |
| 정답·비교 결과 | QA | 각 개발 담당 | 정답 ID와 실제 출력 ID의 매핑 |
| 화면 배치·필터 상태 | 각 화면 담당 | 해당 화면 | 원본 자산 ID를 유지하며 화면 설정만 별도 관리 |

대시보드에서 자산 ID를 다시 생성하거나, 화면 표시만으로 실제 호출·접근 여부를 확정하지 않는 방식을 제안한다.

## 3. 우선 합의할 공통 구조

### C-01. 전달 단위와 공통 식별 정보

**제안:** 초기 연동은 JSON 예제 파일로 검증한다. 자산 스냅샷과 사용량은 각각 전달하되 공통 식별 정보로 연결한다. 이후 API를 사용하더라도 객체의 의미와 ID는 유지한다.

| 필드 후보 | 의미 | 제안 규칙 |
|---|---|---|
| `schema_version` | 해당 데이터 형식의 버전 | 자산·사용량 계약별로 관리. 문서 버전·MCP 버전과 구분 |
| `environment_id` | 데이터를 수집한 환경 | 환경 이름 대신 안정 ID 사용. 로컬·클라우드 환경 구분 |
| `producer` | 생성 모듈과 구현 버전 | `name`, `version` 기록 |
| `generated_at` | 전달 데이터를 생성한 시각 | 시간대가 포함된 시각 사용 |
| `snapshot_id` / `record_id` | 스냅샷 또는 사용량 기록 ID | 새 스캔은 새 스냅샷 ID. 같은 기록의 재전송은 같은 ID 유지 |

**협의 질문:** 최초 연동은 파일로 가능한가? 환경 ID는 누가 발급하는가? 사용량 기록 수정 시 같은 ID와 수정 버전을 쓸지 새 기록으로 교체할지?

### C-02. 자산 스냅샷의 최소 묶음

**제안:** 다음 항목을 자산 전달의 기본 구조로 둔다. 분석 모듈이 정해지기 전에는 보안 경고 생성을 스캐너의 의무로 고정하지 않는다.

| 구성 | 내용 | 필수 여부 제안 |
|---|---|---|
| 공통 식별 정보 | 버전·환경·생성 모듈·생성 시각·스냅샷 ID | 필수 |
| `scan` | 수집 시작·종료 시각, 전체 완료 상태 | 필수 |
| `assets[]` | 수집한 자산 | 필수 |
| `relations[]` | 근거가 있는 자산 관계 | 필수 |
| `evidence[]` | 자산·관계가 참조하는 근거 | 필수 |
| `collection_results[]` | 대상·목록 종류별 성공·부분 성공·실패·미수행 | 필수 |
| `findings` / `assessment_results` | 보안 점검 경고·평가 결과 | 포함 여부와 별도 전달 여부를 후속 결정 |

전체 완료 상태는 개별 수집 결과에서 계산한다. 배열이 비어 있어도 수집 상태를 확인해야 하며, 실패한 수집을 정상적인 빈 결과로 해석하지 않는다.

**협의 질문:** 최초 연동에서 제공 가능한 최소 묶음은 무엇인가? 점검 결과를 같은 스냅샷에 넣을지, 스냅샷을 참조하는 별도 결과로 받을지?

### C-03. 자산의 공통 필드와 ID

| 필드 후보 | 의미 | 필수 여부 제안 |
|---|---|---|
| `asset_id` | 자산의 안정 식별자 | 필수 |
| `asset_type` | 7종 자산 분류 | 필수 |
| `asset_subtype` | Resource와 Prompt 구분 | `resource_prompt`에서 필수 |
| `name` | 화면 표시 이름 | 필수, 공식 이름이 없으면 표시용임을 구분 |
| `official_identifier` | 원천의 이름·URI·패키지 ID 등 | 원천에 존재할 때 |
| `owner_ref` | 선언 주체 또는 소유 서버 참조 | 유형별 의미를 정한 뒤 조건부 필수 |
| `evidence_refs[]` | 수집 근거 참조 | 필수 |
| `mcp` | MCP 객체의 공식 필드 | 해당 객체가 있을 때 |
| `product` | 제품별 설정 정보 | 해당 정보가 있을 때 |
| `project` | 정규화한 공급망·권한·노출 정보 | 상세 구조는 후속 협의 |

자산 유형 후보: `gateway`, `node`, `mcp_server`, `tool`, `resource_prompt`, `skill`, `plugin`. Resource/Prompt는 한 분류 안에서 `resource`, `prompt`로 구분한다.

ID는 다음 원칙부터 합의한다.

- 다른 서버의 동명 Tool은 서로 다른 자산이다. Tool ID에는 소속 서버와 공식 이름이 반영되어야 한다.
- 같은 환경에서 같은 자산을 반복 수집하면 같은 자산 ID를 사용한다. 수집 시각은 자산 ID에 넣지 않는다.
- 서버 ID는 선언 주체·선언 위치·서버 키를 구분한다. endpoint가 같다는 이유만으로 합치지 않는다.
- Skill·Plugin의 설치 위치와 버전 변경을 어떻게 식별할지는 수집 예시를 보고 정한다.
- 참조 대상이 MCP Server이면 별도 ID 체계를 만들지 않고 해당 자산의 `asset_id`를 사용한다. `server_id` 필드를 둔다면 이 ID의 참조라는 의미로 통일한다.

**협의 질문:** 반복 수집 시 유지되는 원천 식별자는 무엇인가? 환경 복제·설정 이동·이름 변경을 새 자산으로 볼 것인가? ID 생성·정규화 로직은 어느 모듈에서 관리할 것인가?

### C-04. 관계와 직접 수집하지 않는 대상

**제안:** `relation_id`, `relation_type`, `source_asset_ref`, `target`, `evidence_refs`, `confidence`를 기본으로 둔다. 추론 관계에는 `inference_rule`을 추가한다.

| 관계 후보 | 시작 → 대상 |
|---|---|
| `DECLARES` | Gateway/Node → MCP Server |
| `ADVERTISES` | MCP Server → Tool/Resource/Prompt |
| `ASSOCIATED_WITH` | Skill/Plugin → MCP Server/Tool |
| `MAY_EXPOSE_TO` | 관련 자산 → Agent 참조 |
| `MAY_ACCESS` | 관련 자산 → 잠재 접근 자원 |
| `MAY_SEND_TO` | 관련 자산 → 잠재 외부 목적지 |

`target`은 종류에 따라 구분한다. 아래 두 예시는 대상 표현만 보여주는 조각이다.

```json
{"kind": "asset", "asset_ref": "asset-server-001"}
```

```json
{"kind": "backend_resource", "resource_kind": "filesystem", "scope_category": "workspace"}
```

Agent·접근 자원·외부 목적지는 속성 기반 참조로 표현하고, 7종 직접 수집 자산 수에 추가하지 않는다. 자산 참조는 해당 스냅샷에 존재해야 한다. 관계 ID도 재수집 시 동일 관계를 구분할 수 있도록 생성 규칙을 정한다.

**협의 질문:** 대시보드가 속성 기반 대상을 표현할 수 있는가? 구체적인 목적지를 모르는 경우 범주로 표현할 수 있는가? 최초 연동에서 수집 가능한 관계는 어디까지인가?

### C-05. 근거·상태·미확인 값

| 항목 | 제안 규칙 |
|---|---|
| 근거 | `evidence_id`, `evidence_type`, `source_ref`, `observed_at` 필수. 필요하면 필드 위치와 수집 맥락 추가 |
| 근거 참조 | 비밀값을 제거한 증적 ID 또는 안전한 위치 참조. 원문 전체 전달은 필수가 아님 |
| 신뢰도 | `confirmed`, `high`, `medium`, `low`. 확인한 사실의 신뢰도이며 자산의 안전 등급과 구분 |
| 수집 상태 | `success`, `partial`, `failed`, `not_attempted` 후보. 대상과 수집 범위를 함께 기록 |
| 미확인 값 | 프로젝트 필드는 `null`과 사유로 표현. 공식 MCP 객체의 원래 표현은 유지 |
| 미제공·해당 없음 | 선택 필드 생략은 미제공으로 해석. 해당 없음까지 구분해야 하는 항목은 별도 상태 사용 |
| 빈 목록 | `[]`만으로 존재하지 않음을 확정하지 않음. 해당 범위가 정상 완료됐는지 함께 확인 |
| 정적 노출 상태 | 선언·발견·노출·잠재 호출을 구분. 노출 판정에는 대상 Agent와 정책 맥락 연결 |
| 실제 사용 | 정적 스캐너의 결과만으로 실제 호출·접근·전송을 확정하지 않음 |
| 시각 | 시간대 포함, 저장은 UTC로 통일하는 안 제안. 생성 시각과 관측 시각 구분 |
| 비밀값 | 토큰·Header·환경변수의 실제 값은 전달하지 않음. URL·명령 인자·오류·증적에도 같은 원칙 적용 |

**협의 질문:** 각 모듈이 미확인·미수집·해당 없음을 구분할 수 있는가? 부분 수집 시 기존 화면 데이터를 어떻게 유지할 것인가?

특히 실패한 스냅샷에서 자산이 빠졌다는 이유로 기존 자산을 삭제 처리하지 않는 규칙이 필요하다. 광고 목록은 조회 시각·인가 맥락·목록 수집 완료 여부를 기록해야 비교할 수 있다.

### C-06. 독립된 사용량 데이터와 자산 연결

**제안:** 사용량·비용 데이터는 모니터링 파트에서 별도 정의하고, 아래 연결 규칙부터 합의한다. 실제 호출·접근 이벤트와 사용량 기록을 하나의 객체로 강제하지 않는다.

| 연결·해석 항목 | 제안 |
|---|---|
| 환경 | 자산 스냅샷과 같은 `environment_id` 사용 |
| 관측 단위 | 세션·요청·Agent·모델·Tool 등 실제 확보 가능한 단위를 명시 |
| 시간 구간 | 구간 시작·종료와 경계 포함 규칙 명시 |
| 자산 참조 | 연결 가능한 경우 `asset_ref` 사용. 불가능하면 `null`과 매핑 상태·사유 기록 |
| 스냅샷 참조 | 어느 시점의 자산 목록에 매핑했는지 `snapshot_ref` 기록. 단순히 최신 스냅샷에 연결하지 않음 |
| 값의 성격 | 사용량·비용 각각 측정·추정 여부를 구분. 토큰이 측정값이어도 비용은 추정값일 수 있음 |
| 귀속 근거 | 사용한 원천 식별자, 매핑·추정 방법과 버전 기록 |
| 합산 | 같은 사용량을 세션 총량과 Tool 추정량으로 중복 합산하지 않도록 집계 수준 구분 |

사용량 세부 필드, 단가·통화·가격 기준일, 오차 계산 기준은 모니터링 담당의 예제와 함께 확정한다. Tool별 실제 관측이 불가능한 경우 추정 가능 범위를 명시하고, 상위 단위 사용량을 Tool의 실측값으로 표시하지 않는다.

**협의 질문:** 현재 수집 가능한 최소 단위는 무엇인가? 로그의 어떤 키를 자산 ID에 연결할 수 있는가? 매핑 담당은 누구인가? 추정 오차를 비교할 기준값을 확보할 수 있는가?

### C-07. 버전과 변경 처리

**제안:** 필수 필드 삭제·자료형 변경·의미 변경은 호환되지 않는 변경으로 관리한다. 선택 필드 추가는 수신 측의 허용 여부를 확인한 뒤 적용한다.

- 화면은 지원하지 않는 버전을 정상 데이터처럼 처리하지 않고 이유를 표시한다.
- 생산자와 소비자가 같은 예제 데이터로 읽기·표시·비교를 확인한 뒤 계약을 확정한다.
- 변경 기록에는 버전, 변경 이유, 영향 모듈, 예제 수정 여부, 적용 시점을 남긴다.

**협의 질문:** 계약 문서·예제 파일 관리자는 누구인가? 이전 버전을 언제까지 지원할 것인가? 어떤 담당자의 확인 후 적용할 것인가?

## 4. 담당자별 사전 준비 자료

아래는 협의를 위한 요청안이며 담당 배정·기한은 회의에서 확인한다. 완성된 구현 대신 비밀값을 제거한 수집 예시나 예상 출력으로도 검토할 수 있다.

| 담당 영역 | 준비할 자료 | 확인 목적 |
|---|---|---|
| 스캐너 — 김규민 | Gateway/Node–Server–Tool 예제, 수집 가능 필드·불가능 필드, 부분 실패 예제 | ID·기본 구조·수집 상태 결정 |
| 대시보드 — 고혜림 | 첫 화면에 필요한 최소 데이터와 필수/선택 구분, 누락 데이터 표시안 | 생산자가 제공할 수 있는 데이터와 화면 요구 조정 |
| 모니터링 — 이정철 | 사용량 기록 1건, 관측 단위, 자산 연결에 쓸 수 있는 키, 측정·추정 구분 | 별도 데이터 계약과 자산 연결 규칙 결정 |
| 테스트베드 — 박병하 | 환경·인스턴스 구분표, 초기화·복제 방식, 기준 환경 식별안 | 환경 ID와 재현 조건 결정 |
| QA — 정서진 | 정답 ID 매핑 예제, 누락·중복·부분 수집의 기대 처리 | 계약 검증 기준 결정 |

보안 이벤트 상세 요구사항은 해당 담당자에게 별도로 확인한다. 이번 자료 준비에 시나리오 재작성은 포함하지 않는다.

## 6. 합의 후 작성할 산출물

1. 합의한 공통 필드의 필수 여부·자료형·허용값을 담은 데이터 계약 v0.1.
2. 정상 수집, 일부 수집 실패, 다른 서버의 동명 Tool을 포함한 자산 예제.
3. 자산 연결 성공·미확인 사례를 포함한 사용량 예제. 수집 단위가 정해진 후 작성.
4. 예제의 ID 중복·참조 무결성·미확인 상태·비밀값 제거 및 화면 표시 확인 결과.

세부 필드가 미정인 모듈은 보류 항목을 남기고, 합의된 공통 구조부터 구현한다. 회의 완료는 전체 스키마 확정을 의미하지 않는다.
