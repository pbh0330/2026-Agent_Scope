# AI Agent Asset Visualization Dashboard Specification

> AI 에이전트 자산 가시화 대시보드 설계 및 구현 규격

| 항목 | 값 |
|---|---|
| 문서 버전 | **v3.0** (2026-11-17) · v2.0: 2026-11-15 · v1.0: 2026-10-01 |
| 작성 | 위협 시나리오·대시보드 파트 |
| 기준 데이터 계약 | 공통 스키마 `0.7.0-draft` (문서 [schema-design-draft.md](../schema-design-draft.md) v0.7.7). 출력 전환 완료 |
| 기준 위협 규칙 | 위협 시나리오 v2.1 ([docs/threat-scenarios](../threat-scenarios/README.md)) |
| 구현 | `dashboard/` (feature/dashboard) |
| 적용 범위 | OpenClaw + MCP 환경의 정적 자산·관계·보안 평가 가시화, 토큰 사용량 표시 |

v3.0은 멘토링 피드백("대시보드는 실제 사용자가 보는 제품 화면이다")에 따라 **화면을 8개에서 3개로 줄이고**, 테스트·검증용 화면은 결과 파일로만 남겼다. 데이터 모델(8종 자산, 6단계 상태, 평가 결과 6종)은 v2.0과 같고, 출력은 공통 스키마 `0.7.0-draft`로 전환했다. v2.0과의 차이는 [15절](#15-v20--v30-변경)에 있다.

## 1. 목적

대시보드는 에이전트 환경을 운영하는 사용자가 다음 세 질문에 답할 수 있게 한다. 화면 하나가 질문 하나에 답한다.

| 질문 | 화면 |
|---|---|
| 지금 안전한가? | 자산 현황 |
| 에이전트가 무엇에 연결돼 무엇을 할 수 있나? | 자산 지도 |
| 무엇을 고쳐야 하나? | 위협과 조치 |

기대 결과 대조, 스냅샷 변경 비교, 수집 검증은 팀 검증용이라 화면에 두지 않고 결과 파일(`expected.json`, `diffs/`, `qa.json`)로 만든다. 발표에서 탐지 시연이 필요하면 따로 캡처해 쓴다.

## 2. 설계 원칙

| 원칙 | 내용 |
|---|---|
| 사용자 화면 | 테스트 용어·파일 이름·설정 이름을 화면 본문에 쓰지 않는다. 원래 값은 "세부 정보 보기"에만 둔다 |
| 근거 우선 | 모든 판정·경고·관계는 근거(evidence)로 거슬러 올라갈 수 있어야 한다. 근거 없는 간선·판정은 그리지 않는다 |
| 미확인 ≠ 정상 | `null`·`unknown`·`not_evaluated`·`error`를 "안전"으로 표시하지 않는다. 수집 실패와 삭제를 구분한다 |
| 정적 우선 | 정적 분석으로 `CALLABLE`·`USED`를 판정하지 않는다. 사용 기록은 상태를 바꾸지 않고 따로 표시한다 |
| 비밀값 비수집 | 실제 비밀값은 수집·저장·표시하지 않는다. 참조 이름·저장 위치·존재 여부만 표시한다 |
| 원천 비신뢰 | 서버가 보낸 설명·스키마는 신뢰하지 않는 데이터로 텍스트로만 표시한다 |
| 계약 소비자 | 대시보드는 공통 계약 파일만 읽는다. 스캐너 내부 형식은 어댑터(`pipeline/`)를 거친다. 형식이 틀린 파일은 그리지 않는다 |

## 3. 데이터 흐름

```text
feature/scanner-config   스캐너: 설정 수집(mcp.servers, nodeHost.mcp.servers), --plugin-manifest, tools_catalog
testbed (develop, #24)   profiles/<구성>, ground-truth/raw/<구성>, 정답, approved-servers.json
docs/threat-scenarios    시나리오 카탈로그 v2.1, S2 기준 정책, 기대 결과
token-collector          사용 현황 API(usageapi)
          │
          ▼
dashboard/pipeline/build_data.py   어댑터 + 정적 탐지기 + 비교기
          │
          ▼
dashboard/public/data/*.json       공통 계약 파일 (0.7.0-draft)
          │                         pipeline/check_schema.py로 형식 점검
          ▼
dashboard (React)                  계약 검사 → 화면 3개
```

토큰 사용은 API가 켜져 있으면 실시간으로 읽고(`/api/v1/usage`), 꺼져 있으면 파이프라인이 저장한 응답 사본을 읽는다.

## 5. 자산 8종

| `asset_type` | 화면 표기 | 하위 유형(`asset_subtype`) | 소속(`owner_ref`) |
|---|---|---|---|
| `gateway` | 게이트웨이 | — | — |
| `node` | 노드 | — | — |
| `mcp_server` | MCP 서버 | — | 선언 주체(Gateway·Node·Plugin) |
| `tool` | 도구 | — | 소속 서버 |
| `resource_prompt` | 리소스·프롬프트 | `resource`, `resource_template`, `prompt` | 소속 서버 |
| `skill` | 스킬 | — | — |
| `plugin` | 플러그인 | — | — |
| `permission_auth` | 권한·인증 | `permission`(권한 정책), `authentication`(인증 참조) | — (`project.permission_auth.target_refs`로 적용 대상) |

- 다른 서버의 같은 이름 도구는 별도 자산이다(QA-UI-02).
- 모든 자산의 `context.gateway_ref`는 같은 스냅샷의 Gateway `asset_id`다(12.7, QA-INT-01).
- 자산 ID는 협의안 B(`<접두사>_<sha256(환경\n canonical key)[:16]>`)를 쓰며, ID 규칙 확정 시 `pipeline/agentscope_pipeline/ids.py`만 바꾼다.
- 토큰 사용량은 자산 종류로 추가하지 않는다. 자산에 딸린 사용량으로 표시한다(2026-11-17 결정).

## 6. 상태

`project.state_assessments[]`의 6단계를 보존한다. 화면은 사용자가 이해할 수 있는 두 가지만 앞에 보여 준다.

| `state` | 화면에서 | 정적 단계에서 |
|---|---|---|
| `DECLARED` | 승인 여부·등록 위치 표시의 근거 | 설정 근거로 판정 |
| `DISCOVERED` | "세부 정보 보기" | 설치 파일·목록 응답 근거로 판정 |
| `EXPOSED` | 도구 칸 색(초록 = 에이전트에 보임, 회색 = 막힘·확인 못 함). 회색 칸에 마우스를 올리면 이유 | 에이전트 노출 목록(`mcp probe`, `nodes describe`)이 있을 때 판정 |
| `POTENTIALLY_CALLABLE` | 표시 안 함 | 미평가 |
| `CALLABLE` | 표시 안 함 | 판정하지 않음 |
| `USED` | 표시 안 함. 토큰 수집기 기록은 "AI 사용량"에 따로 | 판정하지 않음 |

`EXPOSED = null`인 도구는 "확인 못 한 도구"로, `false`는 "막힌 도구"로 이유와 함께 구분한다.

## 7. 관계

| `relation_type` | 화면 표기 | 출발 → 대상 |
|---|---|---|
| `ADVERTISES` | 도구·리소스 제공 | Server → Tool/Resource/Prompt |
| `DECLARES` | 설정에 등록 | Gateway/Node → Server·Skill, Gateway → Plugin |
| `APPLIES_TO` | 권한 적용 | 권한 정책 → Gateway·Server (구현 관계) |
| `AUTHENTICATES` | 접속 인증 | 인증 참조 → Server (구현 관계) |
| `ASSOCIATED_WITH` | 함께 쓰임 | Plugin → Server(manifest가 등록), Skill → Server(스킬이 쓰는 서버) |
| `PAIRED_WITH` | 기기 연결 | Gateway → Node. 페어링 원본(`devices list`)이 있을 때만. P0는 원본이 없어 없음 |

- 추론 관계(`MAY_EXPOSE_TO` 등)는 만들지 않는다.
- 자산 지도 위쪽 "자산 사이 관계"는 저장된 고유 `relation_id`만 종류별로 세고 방향(출발 자산 종류 → 대상 자산 종류)을 함께 적는다. 지도의 보조 선·Gateway 묶음은 세지 않는다(QA-UI-01).

## 8. 위협 평가와 화면 표기

DetectionReport의 **평가(evaluations)를 항상 함께 읽는다.** 경고만으로는 "안전"과 "판단할 수 없음"을 구분할 수 없기 때문이다.

### 8.1 조건별 결과

| `result` | 화면 표기 | 판정 수에 넣나 |
|---|---|---|
| `detected` | 위협 | 넣음 |
| `not_detected` | 안전 | 넣음 |
| `unknown` | 확인 못 함 + 이유 한 줄 | 넣음 |
| `error` | 확인 못 함 + 이유 한 줄 | 넣음 |
| `not_applicable` | 해당 없음 (표시 안 함) | 넣지 않음 |
| `not_evaluated` | 미점검 (이번 버전에서 검사하지 않는 조건) | 넣지 않음. 대신 시나리오 표기에 반영 |

"확인 못 함"의 이유는 조건별 문장으로 보여 준다(예: S5-C3 "https 연결인데 인증서 확인 설정이 적혀 있지 않아요. 프로그램 기본값에 따라 달라져요.").

### 8.2 시나리오별 표기

자산 현황의 시나리오 목록은 시나리오마다 하나만 표시한다. 우선순위는 다음과 같다.

**위협 n > 확인 못 함 n > 미점검 n > 안전 > 점검 대상 없음**

- 검사하지 않은 조건이 하나라도 있으면 그 시나리오를 "안전"이라고 하지 않는다. 지금 S4(S4-C4)와 S5(S5-C4·C5)는 위협이 없으면 "미점검"으로 나온다.
- 시나리오를 누르면 위협과 조치 화면으로 가고, 위협이 없으면 "점검한 조건에서는 위협이 나오지 않았지만, 검사하지 않은 조건이 n개 있어서 안전하다고 확정할 수 없어요"와 이유를 바로 펼쳐 보여 준다.
- 적용할 대상이 없으면(예: 원격 서버가 없는 구성의 S5) "점검 대상 없음"이다.

### 8.3 경고

- `severity`는 매우 높음·높음·보통·낮음·참고로 목록에 표시하고, `confidence`는 "세부 내용 보기"에 "근거의 확실성"으로 따로 표시한다. confidence는 공격 성공 확률이 아니다.
- 경고마다 무슨 위협인지, 어떤 자산인지(종류·이름·위치), 해야 할 일, 세부 내용(조건 ID, 근거, 기준 정책)을 보여 준다.
- 문구는 자산 성격에 맞춘다. 예: 같은 S1-C2라도 원격 서버는 "연결 주소가 바뀌었어요", 로컬 서버는 "서버 실행 설정이 바뀌었어요".

### 8.4 S1~S5 조건

조건 정의와 기본 severity/confidence는 `scenario-catalog.json`이 원본이다.

| 시나리오 | 화면 이름 | 조건 | 판정 기준 |
|---|---|---|---|
| S1 | 승인 안 된 서버 | C1 미승인 서버, C2 Endpoint·실행 설정 불일치, C3 미승인 Plugin 등록, C4 선언 위치 이상 | `approved-servers.json` |
| S2 | 도구 권한 과다 | C1 필터 밖 도구 노출, C2 파일 범위 과다, C3 명령·네트워크 입력, C4 인증정보 입력 | `expected-tool-policy.json` |
| S4 | 토큰 공유 | C1 같은 저장소 공유, C2 다른 저장소 같은 이름(확인 못 함), C3 미승인 Endpoint 전송, C4 범위 과다(미점검) | 참조 이름·저장 위치, `approved-servers.json` |
| S3 | 도구 이름 겹침 | C1 정의 다름, C2 정의 같음, C3 한쪽 미수집(확인 못 함) | 서버가 광고한 정의 |
| S5 | 약한 연결 보안 | C1 평문 전송, C2 인증서 검증 끔, C3 sslVerify 없음(확인 못 함), C4·C5 미점검 | 선언된 url·sslVerify |

## 9. 집계 규칙

| 표시 | 계산 |
|---|---|
| 식별된 자산 | 8종 고유 `asset_id` 수. Gateway·permission_auth 포함 |
| 위협 자산 | 경고의 `asset_ids` 합집합 크기. 자산 하나에 경고가 여러 개여도 한 번 |
| 에이전트에 보이는 도구 | `EXPOSED = true`인 Tool 수 / 전체 Tool |
| 고쳐야 할 위협 | 선택 스냅샷 detections의 `alerts` 수 |
| 도구 노출(링) | 에이전트에 보이는 도구 / 전체 도구 |
| 승인된 MCP 서버(링) | 승인 목록과 맞는 서버 / 전체 MCP 서버 |
| 위협이 있는 MCP 서버(링) | 경고가 하나 이상인 서버 / 전체 MCP 서버 |
| 자산 사이 관계 | 고유 `relation_id` 수(종류별) |
| AI 사용량 | 사용 현황 API `summary.attributed_tokens` |

## 10. 화면

### 10.1 자산 현황 — 지금 안전한가?

| 영역 | 내용 |
|---|---|
| 위협 배너 | 고쳐야 할 위협 수와 대표 문구 두 개. 위협이 없으면 초록 배너 |
| 핵심 수치 4개 | 식별된 자산, 위협 자산, 에이전트에 보이는 도구, AI 사용량 |
| 자산 유형 | 8종 도넛과 종류별 개수 |
| 노출과 위협 | 링 3개(도구 노출, 승인된 MCP 서버, 위협이 있는 MCP 서버) |
| 위협 시나리오 | S1~S5 시나리오별 표기([8.2절](#82-시나리오별-표기)). 누르면 위협과 조치로 이동 |

### 10.2 자산 지도 — 무엇에 연결돼 무엇을 할 수 있나?

| 영역 | 내용 |
|---|---|
| 자산 8종 | 종류별 개수·한 줄 설명·위협 수 |
| 자산 사이 관계 | 관계 종류별 개수와 방향([7절](#7-관계)) |
| 구조도 | 3열: 어디서 실행되나(게이트웨이·노드와 소속 권한·인증·플러그인·스킬 묶음) → 무엇이 연결됐나(MCP 서버) → 무엇을 할 수 있나(도구 칸·리소스 수). 위협이 있는 자산은 빨간 테두리와 위협 수 |
| 상세 패널 | 상자를 누르면 오른쪽에 열림. 이 자산의 위협과 할 일, 연결된 자산, 서버의 도구, AI 사용량(연결된 경우), 세부 정보 보기(원래 이름·경로·설정 값) |
| 점검 범위 | 이번 점검에서 확인한 것과 못 한 것([14절](#14-데이터-처리-원칙)) |
| AI 사용량 | 사용 흐름(시간대별 토큰), 어디에 썼나(도구가 하는 일 기준 이름) |

### 10.3 위협과 조치 — 무엇을 고쳐야 하나?

| 영역 | 내용 |
|---|---|
| 시나리오 필터 | 전체, S1~S5 |
| 위협 목록 | 처음에는 모두 접힘. 누르면 그 자리에서 펼침 |
| 위협 상세 | 무슨 위협인가요?(제목·이유) → 어떤 자산인가요?(종류·이름·위치, "자산 지도에서 위치 보기") → 해야 할 일 → 세부 내용 보기(조건 ID, 근거, 기준 정책) |
| 확인 못 한·점검하지 않은 항목 | 개수와 이유. 위협이 없는 시나리오를 열면 처음부터 펼침 |

경고를 누르면 자산이, "세부 내용 보기"를 누르면 판정 조건·근거·기준 정책이 나온다. 두 번 클릭으로 근거까지 간다(QA-UI-03).

### 10.4 이름 규칙

- 설정 이름(`fs-workspace`, `tb-gw` 등)에서 뜻을 추측하지 않는다. 팀원이 예시로 붙인 이름이라 실제 사용자 환경과 다르다.
- 자산 이름은 **종류 + 수집한 속성 + 번호**로 만든다. 예: 로컬 MCP 서버 1, 원격 MCP 서버 1, 플러그인 2, 인증 토큰 · 원격 MCP 서버 1.
- 연결 방식(`transport`, `url`, `command`)을 확인하지 못한 서버는 로컬로 추정하지 않고 "MCP 서버 n"으로 쓴다.
- 도구 이름은 서버가 정한 이름이라 그대로 쓴다. 사용량의 도구 이름은 하는 일 기준(파일 읽기, 폴더 목록 보기)으로 바꿔 쓴다.
- 원래 이름·경로·ID는 "세부 정보 보기"에만 둔다.

## 11. 스냅샷

실제 사용자는 자기 환경 하나만 보므로 화면에 스냅샷 고르는 메뉴를 두지 않는다. 기본은 S1이고, 시연·캡처할 때 주소 끝에 구성 키를 붙여 바꾼다(`#P2`, `#S5-T3` 등).

| 구성 | 종류 | 출처 |
|---|---|---|
| P0, P1, P2 | 정상군 | 테스트베드 SNAP-2 설정·수집본, 정답 목록 비교 |
| S1, S2, S4, S3 | 위험 구성 · VM 수집 | SNAP-3 수집본(PR #24) |

## 12. 결과 파일 (화면 없음)

기대 결과 비교(`expected.json`)는 테스트베드 정답 파일(`ground-truth/<구성>.json`의 `expected_*`)을 우선 쓰고, 없으면 `docs/threat-scenarios/expected-results.md`를 쓴다.

| 항목 | 규칙 |
|---|---|
| 일치 | 같은 `condition_id` + 대상 자산(`asset_key`)이 경고에 포함 |
| 나와야 할 경고 (`required: true`) | 없으면 불일치. 탐지율 분모에 포함 |
| 동반 경고 (`required: false`) | 나오면 일치, 안 나오면 "나오지 않음". 분모 제외 |
| 심각도 차이 | 경고는 맞고 severity만 다르면 PARTIAL |
| 판단 불가 유지 | 그 조건 평가가 모두 `unknown`이어야 일치 |
| 나오면 안 되는 경고 | 대상에 해당 시나리오 경고가 나오면 오탐 |

기대 결과 비교는 P2와 위험 구성 8개 모두 PASS다. 변경 비교(`diffs/`)는 P0 → P1 → P2, P2 → 각 위험 구성의 자산·관계·경고 변화를 담고, `not_observed`는 삭제 수에 넣지 않는다. 정답 목록 비교(`qa.json`)는 정상군의 수집률이다.

## 13. 토큰 사용

- 토큰은 별도 화면이 아니라 자산에 딸린 정보로 보여 준다. 자산 현황의 핵심 수치 하나, 자산 지도 아래 "AI 사용량", 서버 상세 패널의 서버별 사용량.
- 사용 현황 API 응답 필드를 그대로 쓴다(`src/types/contracts.ts`의 Usage* 타입).
- 계산하지 못한 토큰(`null`)을 0으로 바꾸지 않는다(QA-USAGE-03).
- 자산 연결은 API가 매핑한 `asset_id`만 쓴다. 이름이 비슷해도 임의로 연결하지 않는다(QA-USAGE-01). 연결되지 않은 기록이 있으면 그 사실을 안내한다.
- 사용 기록은 자산 상태 `USED`를 바꾸지 않는다(스키마 14.2).
- 모든 토큰·비용은 추정치다.

## 14. 데이터 처리 원칙

| 항목 | 규칙 |
|---|---|
| 계약 검사 | 화면을 그리기 전에 형식 버전(`0.7.0-draft`만), ID 중복, 없는 자산·근거·수집 작업·평가 참조, 잘못된 TargetRef를 검사한다. 하나라도 있으면 화면을 그리지 않고 "파일 · 위치 · 원인"을 보여 준다. 구버전을 버전 문자열만 보고 받아들이지 않는다(QA-SCHEMA-02·04) |
| 부분 수집 | `scan.status = partial`과 수집 작업의 `partial`·`failed`·`not_attempted`는 오류가 아니라 정상 결과로 받는다. 자산 지도 "점검 범위"에 확인한 것과 못 한 것을 보여 준다(설정 파일, 서버별 도구 목록, 에이전트 노출 여부, 실패한 작업) |
| 수집 실패와 빈 목록 | 도구 목록 수집에 실패한 서버는 "도구 없음"이 아니라 "도구 목록 확인 못 함"으로 표시한다(QA-COL-06·08) |
| 비밀값 | 비밀번호, API 키, 토큰, 개인 키 값은 수집·표시하지 않는다. 비밀값은 "값은 읽지 않고 이름만 기록"으로 안내한다 |
| 근거 | 경고 → 자산 → 근거(`evidence`) → 원천 설정 경로까지 이동 가능 |
| 원천 텍스트 | 서버 설명·스키마는 텍스트로만 표시하고 실행·링크로 해석하지 않는다 |
| 경로·개인정보 | 출력 파일에 실행 PC의 절대 경로, 팀원 실명을 남기지 않는다. 담당은 역할 이름으로 쓴다 |

## 부록 A. v1.0 → v2.0 변환

스키마 12.8절 대응표를 따른다.

| v1.0 | v2.0 | 변환 규칙 |
|---|---|---|
| `MCP_SERVER` 등 대문자 유형, 7종 | 소문자 `asset_type` 8종 | Gateway는 `gateway` 자산, Resource/Prompt는 `resource_prompt` + subtype, 권한·인증은 `permission_auth` |
| 단일 `state` | `project.state_assessments[]` | 상태별 값·근거·대상 표시 |
| Asset `source` | `product.source_ref`, `evidence_refs` | |
| Asset `confidence` | 상태·관계·탐지 결과별 confidence | 자산 전체에 일괄 부여하지 않음 |
| Relation `source`/`target` | `source_asset_ref` / `target`(TargetRef) | |
| `PROVIDES` | `ADVERTISES` | 서버 목록 근거가 있을 때만 |
| `CONNECTS_TO` | `DECLARES`(선언), `PAIRED_WITH`(페어링) | 선언을 연결 성공으로 바꾸지 않음 |
| `EXPOSES`, `USES` | 상태 `EXPOSED`, 사용 기록 | 관계로 만들지 않음 |
| `CONTAINS`, `REFERENCES`, `AUTHENTICATES` | `ASSOCIATED_WITH`, `permission_auth.target_refs`, 구현 관계 `APPLIES_TO`·`AUTHENTICATES` | 공통 후보에 없는 관계는 구현 관계로 표시하고 합의 전 늘리지 않음 |
| `HIGH/MEDIUM/LOW` | `high/medium/low` | severity와 confidence 분리 |
| `Normal/Warning/High` | 평가 결과 6종 + 경고 severity | unknown·not_evaluated·error를 Normal로 표시하지 않음 |
| `SNAP-S1` 등 | `SNAP-3-S1`, 설정 사본 구성 | 위험 구성 이름은 테스트베드 기준 |
