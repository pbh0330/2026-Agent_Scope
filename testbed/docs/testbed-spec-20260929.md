## 1. 추진 개요

### 본 문서의 목적

- 5~6주차 계획인 "테스트베드 구축 및 클린 스냅샷 확보"의 착수 기준(환경·버전·스냅샷) 확정
- 스캐너·토큰 수집·대시보드·위협 시나리오 검증이 동일한 기준 환경에서 재현되도록 기준선 제공
- 09.15 조사 결과(설정의 게이트웨이·노드 이원화)에 따른 가상머신 2대 구성의 구체화

### 사양 확정 원칙

- **재현성**: 모든 구성요소는 버전으로 고정하고, 단계별 스냅샷으로 언제든 되돌릴 수 있어야 함
- **격리**: 실제 계정·비밀값을 사용하지 않고 실습망 내부에서 완결되도록 구성
- **정답 목록 선작성**: 스캐너 검증 지표(S1 선언 계층·S2 광고 계층 수집률)의 기준을 구성과 동시에 작성

## 2. 확정 사항

09.15 회의에서 도출한 가상머신 2대 구성을 기준으로 환경, 버전, 스냅샷 체계, 정상군 구성을 아래와 같이 정한다.

### 2.1 테스트베드 구성 (가상머신 2대)

| 구분 | 게이트웨이 VM (`tb-gw`) | 노드 VM (`tb-node`) |
|---|---|---|
| 역할 | OpenClaw 게이트웨이, 게이트웨이 측 MCP 서버(`mcp.servers`) | 헤드리스 노드 호스트, 노드 측 MCP 서버(`nodeHost.mcp.servers`)·스킬 |
| 운영체제 | Ubuntu 24.04.5 LTS (x86_64) | Ubuntu 24.04.5 LTS (x86_64) |
| 자원 | vCPU 2 / RAM 6GB / 디스크 150GB | vCPU 2 / RAM 4GB / 디스크 80GB |
| 네트워크 | VMware NAT(VMnet8), 고정 IP | VMware NAT(VMnet8), 고정 IP |
| 게스트 도구 | open-vm-tools | open-vm-tools |
| 현황 | 생성·OS 설치 완료 | 생성 예정(5주차) |

하이퍼바이저는 VMware Workstation(가상 하드웨어 버전 22)이며, 호스트는 Xeon W-2123 8스레드, RAM 64GB로 2대 동시 구동에 여유가 있다. 노드 VM은 게이트웨이 VM과 같은 ISO로 설치하여 OS 차이를 없앤다.

> 변경 이력: 09.22 개발계획서의 "로컬 VM 1대 + AWS EC2 2대" 구성에서, 09.15 조사 결과(게이트웨이·노드 설정 이원화)를 반영해 로컬 VM 2대 구성으로 확정함

### 2.2 버전 고정

| 구성요소 | 고정 버전 | 근거 |
|---|---|---|
| OpenClaw | 2026.9.6 | 2026.09.28 기준 npm 최신판. MCP 설정 지원이 최근 도입된 기능(이슈 #43509)이므로 버전 고정이 필수 |
| Node.js | 24.x LTS (24.16 이상) | OpenClaw 실행 요구사항(`>=24.16.0 <25`) |
| MCP 규격 | 2026-07-28 | 「MCP 공격 표면 정의 v2.0」의 기준 규격과 일치 |
| 기준 문서 | openclaw 저장소 `v2026.9.6` 태그의 `docs/` | 문서와 실제 동작의 버전 불일치 방지 |
| 자동 업데이트 | 비활성화 | 실험 중 버전 변동으로 인한 결과 오염 방지 |

### 2.3 스냅샷 체계

| 스냅샷 | 상태 | 용도 |
|---|---|---|
| SNAP-0 | OS 설치 + 기본 패키지 + open-vm-tools, Node.js 설치. OpenClaw 미설치 | 재설치 없이 초기 상태로 복귀 |
| SNAP-1 | OpenClaw 2026.9.6 설치, 게이트웨이·노드 페어링 완료. MCP 서버·스킬·플러그인 없음 | 스캐너 "0건" 기준선, 오탐 측정, 내장 보안 감사 실행 |
| SNAP-2 | 정상군(프로파일 P0/P1/P2) 구성 적용 완료 | 위협 시나리오 주입 전 기준 상태 |
| SNAP-3~ | 위협 시나리오(S1~S5)별 구성 | 시나리오 검증 |

스냅샷은 두 VM을 같은 이름으로 동시에 생성하며, 전원을 끈 상태에서 생성하여 메모리 상태를 포함하지 않는다.

### 2.4 정상군 구성 기준

위협 시나리오(초안)의 각 "정상 상태"를 정상군이 갖춰야 할 조건으로 삼는다.

| 시나리오 | 정상 상태(위협 시나리오 초안) | 정상군 구성 |
|---|---|---|
| S1 | 승인된 Skill·Plugin만 허용된 서버를 등록 | 승인 서버 목록(allowlist)을 문서화하고 해당 서버만 선언 |
| S2 | 조회용 Tool은 제한된 자원만 접근, 고위험 기능은 승인·필터 적용 | 파일 서버는 작업 디렉터리로 한정, `toolFilter.include` 적용 |
| S3 | Tool이 서버별로 고유하게 식별됨 | 서버 간 동명 Tool이 없도록 구성하고 목록으로 확인 |
| S4 | 서버별 최소 범위 자격증명 분리 | 서버마다 별도 자격증명 참조(더미 값, `.env` 참조) |
| S5 | 신뢰된 HTTPS 연결, TLS 검증 활성화 | 원격 서버는 실습용 CA 인증서로 HTTPS, `sslVerify` 활성화 |

### 2.5 정상군 프로파일 (P0/P1/P2)

| 프로파일 | 구성 | 검증 목적 |
|---|---|---|
| P0 최소 | 게이트웨이 단독 + 파일 서버 1종(stdio, `mcp.servers`) | 스캐너 기본 수집 동작 확인 |
| P1 분산 | P0 + 노드 페어링 + 노드 측 서버 2종(stdio, `nodeHost.mcp.servers`) + 노드 스킬 2종 | 설정이 두 곳에 나뉜 상태 재현(1차 공백 실증), 도구·리소스·프롬프트 광고 수집 |
| P2 전체 | P1 + 원격 HTTPS 서버 1종(노드 VM에서 구동, 게이트웨이에 선언) + 서버별 자격증명 + 플러그인 1종 + 게이트웨이 워크스페이스 스킬 1종 | 7종 자산(게이트웨이·노드·MCP 서버·도구·리소스/프롬프트·스킬·플러그인) 전부 포함, S1~S5 정상 기준 |

서버는 MCP 공식 참조 서버(filesystem, memory, everything)와 실습용으로 직접 만든 원격 서버 1종으로 구성하고, 설치 시 패키지 버전을 고정한다. everything 서버는 도구·리소스·프롬프트를 모두 광고하므로 광고 계층(S2) 수집 검증에 사용한다.

### 2.6 정답 목록 및 인터페이스 계약

**정답 목록 (ground truth)**

- 프로파일별로 수작업 정답 목록을 작성한다(자산 식별자, 자산 유형, 선언 위치, 기대 관계).
- 자산 식별자는 v2.0의 복합 식별 방식(서버 식별자 + 자산 유형 + 공식 식별자)을 기준으로 하되, 구체적인 생성 규칙은 공통 스키마 초안(`docs/schema-design-draft.md`)의 합의 결과를 따른다.
- 형식: [../ground-truth/README.md](../ground-truth/README.md)

**관계 명칭**

정답 목록의 기대 관계는 v2.0이 정의한 **1차 정적 스캐너용 관계**를 사용한다. v2.0은 정적 근거만으로 확정할 수 없는 관계를 `MAY_*` 추론 관계로 두고, 런타임 관찰 근거가 확보된 경우에만 확정 관계로 승격한다.

| 1차 정적 관계 (정답 목록에 사용) | 의미 | 런타임 확정 시 승격 |
|---|---|---|
| `DECLARES` | Gateway/Node가 MCP Server를 선언 | - |
| `ASSOCIATED_WITH` | Skill·Plugin이 MCP Server 또는 Tool과 연관 | `REGISTERS` (등록 근거 확보 시) |
| `MAY_EXPOSE_TO` | 정적 정책상 자산이 Agent에 노출될 가능성 | `EXPOSES_TO` |
| `MAY_ACCESS` | 설명·스키마·설정상 자원 접근 가능성 | `ACCESSES` |
| `MAY_SEND_TO` | 설정·스키마상 외부 목적지 전송 가능성 | `SENDS_TO` |

> 정정: 제출본에서는 위협 시나리오 초안과 v2.0의 관계 명칭이 불일치한다고 보고 v2.0 확정 관계명으로 통일할 것을 제안했으나, v2.0 최신본은 위 두 층 구조를 이미 정의하고 있어 불일치가 아님을 확인함. 모든 관계에는 v2.0에 따라 근거(`evidence_refs`)와 신뢰도(`confidence`)를 함께 기록한다.

### 2.7 운영 원칙

- 실제 토큰·API 키는 사용하지 않고 더미 값과 참조 이름만 사용한다(v2.0의 민감정보 수집 원칙과 동일).
- 외부 실계정·SaaS에 연결하지 않으며, 원격 서버도 실습망 내부에서만 구동한다.
- 모든 설정 파일과 정답 목록은 깃허브 작업 브랜치로 관리하고 병합 요청을 거쳐 반영한다.
