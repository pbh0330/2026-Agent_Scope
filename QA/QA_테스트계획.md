# QA 테스트 계획

## 1. 목적

자산 인벤토리 스캐너가 정의된 정적 자산과 관계를 정확하고 안전하게 수집하고, 그래프 대시보드가 그 결과와 위협 경로를 일관되게 표현하는지 검증한다.

QA는 단순 화면 확인이 아니라 다음 질문에 답하는 것을 목표로 한다.

1. 수집 대상 자산이 누락되거나 잘못 합쳐지지 않는가?
2. S1~S5 시나리오의 합의된 위험 상태를 탐지하고 정상 상태를 오탐하지 않는가?
3. 스캐너 출력과 대시보드 입력 사이의 계약이 유지되는가?
4. 비밀값을 수집·저장·표시하지 않는가?
5. 같은 환경에서 결과를 재현할 수 있는가?

## 3. 검증 범위

### 3.1 포함 범위

- 8종 정점: Gateway, Node, MCP Server, Tool, Resource/Template/Prompt, Skill, Plugin, Permission/Auth
- 하위 유형: resource_prompt의 resource/resource_template/prompt, permission_auth의 permission/authentication
- 정적 관계 후보: `DECLARES`, `PAIRED_WITH`, `ADVERTISES`, `ASSOCIATED_WITH`, `MAY_EXPOSE_TO`, `MAY_ACCESS`, `MAY_SEND_TO` (이름·방향·생성 담당 합의 후 판정)
- Permission/Auth 적용 대상 참조와 중복 집계 방지, 선언 주체와 실행 위치 구분
- 구버전 입력의 명시적 변환, 정상 0건·미지원·조회 실패 구분
- 선언·공급망·발견·권한 계층의 정적 스냅샷
- 스캐너 출력 스키마 유효성
- 스캐너와 대시보드 간 데이터 전달
- S1~S5 중 QA 범위로 합의한 위협 상태와 대응 정상 상태
- 오류 처리, 반복 실행, 회귀 테스트
- 비밀값 미수집과 로그·화면 비노출

### 3.2 제외 범위

- 실제 공격 성공 여부를 확인하는 침투 테스트
- 공격 페이로드 실행

## 4. 역할 및 협업 지점

| 영역 | 주 담당 | QA 확인 사항 |
|---|---|---|
| QA·테스트베드 검증 | 정서진 | 합격 조건, 테스트 케이스, 결과 및 결함 관리 |
| 자산 식별 스캐너 | 김규민 | 정점·관계·필드 수집 결과와 오류 처리 |
| 그래프 대시보드 | 고혜림 | 스키마 수용, 자산·관계·경고 표시 |
| 토큰 사용량 수집 | 이정철 | 데이터 확보 가능 범위와 후속 런타임 지표 |
| 테스트베드 구축 | 박병하 | 2대 구성, 기준 스냅샷, 재현 환경 |

공통 데이터 스키마, 스캐너 출력, 대시보드 입력 또는 모듈 간 인터페이스가 변경되면 관련 담당자와 합의하고 영향받는 테스트를 다시 수행한다.

위협 시나리오 작성·확정은 시나리오/대시보드 담당 파트에서 수행한다. 현재 S1~S5를 계획된 필수 시나리오로 삼는다. QA는 확정 문서·버전, 정상/위협 구성, 기대 경고·근거와 제공 데이터를 인수해 각 테스트의 세부 검증 조건을 확정한다. 런타임 이벤트/로그 검증은 스키마·데이터 제공 방식·검증 범위 합의 후 추가한다.

## 6. 진입 및 종료 기준

### 6.1 진입 기준

- [ ] 테스트할 PR 또는 commit이 식별되어 있다.
- [ ] 출력 스키마 버전과 필수 필드가 합의되어 있다.
- [ ] 8종별 지원 범위와 미지원·미수집 사유가 확인되어 있다.
- [ ] 구버전 입력의 변환기·ID/참조 매핑과 보완 증적이 확인되어 있다.
- [ ] 정답은 비교 범위의 full 목록이며 차분 구성은 적용 규칙에 따라 물질화했다.
- [ ] Gateway·Node 기준 스냅샷이 확보되어 있다.
- [ ] 정답 자산·관계·경고 목록이 작성되어 있다.
- [ ] 테스트용 비밀값은 실제 운영 자격증명과 분리되어 있다.
- [ ] 실행 방법과 로그·출력 위치를 알고 있다.

### 6.2 종료 기준

시나리오 관련 테스트는 확정 문서와 기대 조건을 인수한 뒤 실행한다. 기준 미확정으로 실행할 수 없으면 `Blocked`와 사유를 기록한다. 공통 테스트는 자체 사전 조건 충족 시 실행할 수 있다.

- [ ] 계획된 필수 테스트를 모두 실행했다.
- [ ] 보안 및 데이터 무결성 관련 Critical·High 결함이 없다.
- [ ] 실패 테스트가 수정되었거나 잔여 위험으로 명시적으로 승인되었다.
- [ ] 수정 기능의 재검증과 관련 회귀 테스트를 완료했다.
- [ ] 수집 정확도·오탐·시나리오 기대 조건 충족률·소요 시간을 기록했다.
- [ ] 실행 환경, 결과 및 증적만으로 다른 팀원이 재현할 수 있다.

## 7. 측정 지표

| 지표 | 계산식 | 목표치 |
|---|---|---|
| 자산 수집 재현율 | 올바르게 수집된 자산 수 / 정답 자산 수 | 기준 실행 후 합의 |
| 수집 자산 중 오탐 비율 | 정답에 없는 수집 자산 수 / 전체 수집 자산 수 | 기준 실행 후 합의 |
| 관계 정확도 | 올바른 관계 수 / 출력된 전체 관계 수 | 기준 실행 후 합의 |
| 시나리오 기대 조건 충족률 | 충족한 기대 조건 수 / 실행한 합의된 기대 조건 수 | 조건 목록 확정 후 합의 |
| 정상 환경 오탐 수 | 정상 상태에서 발생한 부당 경고 수 | 기준 실행 후 합의 |
| 수집 소요 시간 | 스캔 시작부터 유효 출력 완료까지 | 서버 수와 함께 기록 |
| 가시화 탐색 단계 | 경고에서 영향 자산·경로 확인까지의 클릭 또는 단계 수 | 기준 실행 후 합의 |

분모가 0인 지표는 0으로 계산하지 않고 `N/A`로 기록한다.

전체 자산은 8종의 고유 asset_id 수다. Gateway와 Permission/Auth를 포함하고 Gateway 그룹·Host/Client/Agent 문맥은 제외한다. 하나의 정책을 적용 대상 수만큼 복제하지 않는다. 수집 범위 내 미지원 유형의 정답을 임의로 분모에서 빼지 않고, 합의된 범위 밖 제외와 미지원·실패 범위를 따로 보고한다.

선언 계층(`declared`)과 광고 계층(`advertised`)의 수집 재현율도 각각 기록한다. 비교 대상 프로파일·스냅샷·수집 범위·인증 맥락을 맞추고, 계층 간 중복 자산은 전체 집계에서 중복 계산하지 않는다. 부분 수집 시 누락과 수집 실패 범위를 함께 보고하며 누락을 자산 삭제로 단정하지 않는다.

테스트베드 인수 시 P0는 기본 수집, P1은 분산 수집, P2는 8종 자산 검증에 연결하되 Permission/Auth 정답과 실제 수집 지원을 확인한다. 위협 구성은 기준 프로파일과 변경분을 full 목록으로 만드는 규칙을 확인한다. SNAP-1의 “0건”은 MCP 서버 등 대상 유형별로 확인하고 Gateway·Node를 포함한 전체 자산 0건으로 가정하지 않는다.

## PR #18 반영 기준 (2026-11-13)

- 검토 기준: [PR #18 공통 스키마](https://github.com/pbh0330/2026-Agent_Scope/blob/9085e8deb4820b3c7582224f3e5dbac42e28a52d/docs/schema-design-draft.md) HEAD `9085e8deb4820b3c7582224f3e5dbac42e28a52d`. 문서 개정 v0.7.5와 데이터 계약 `0.7.0-draft`를 구분한다. 기존 PR #1은 8종 분류의 근거로 유지한다. 이 기준은 최종 계약 합의나 구현 완료를 뜻하지 않는다.
- 첫 실행은 최신 스캐너 → #13 기존 어댑터 → 대시보드의 실제 P0 한 건으로 진행한다. 선택한 스냅샷의 환경·프로필·자산 ID를 공유하고 Gateway 참조를 실제 Gateway asset_id에 연결한다. 최종 ID·Permission 전체 합의는 첫 연결의 선행 조건이 아니다. 미합의 조건만 Blocked로 분리한다.
- 검토 fixture는 원천 자산 17개·관계 16개의 변환 예제다. 임시 ID와 가상 시각을 실제 실행 증적으로 사용하지 않는다. #13의 20개 자산은 정책/인증 3개를 별도 대조한다. 관계 18개는 APPLIES_TO 3개 추가·PAIRED_WITH 제외의 차이를 확인한다. 근거 없는 페어링을 만들거나 정책 자산을 개수에 맞춰 제거하지 않는다. APPLIES_TO는 구현 관계로 구분한다.
- 정상 0건·영역 미선언·미지원·조회 실패·partial을 구분한다. fixture의 partial은 가져온 인증 맥락·페이지 완전성 정보 부족이며 실제 조회 실패가 아니다. 실제 상태는 수집 계획·결과로 계산한다. 범위 밖 작업 미수행을 실패로 집계하지 않는다.
- 두 MCP 버전 처리·선언값 수집과 기존 어댑터·정적 탐지·사용량 API는 구현된 경로를 먼저 검증한다. 담당자 테스트 보고와 QA 독립 실행을 구분한다. 스캐너 712개는 테스트 수집 수이며 전체 실행 통과 수가 아니다.

### 첫 연동과 최종 인수의 순서
