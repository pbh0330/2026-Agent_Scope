## 원본 기록과 통제 입력의 차이

원본 `pc-1029.traces.jsonl`은 PC 실측 기록이다. 기준 P2에 없는 `fs__read_text_file` 등을 포함하므로 16건 전부 미귀속인 것이 정상이다. 환경/프로필 인자를 P2에 맞췄다고 PC 기록이 VM 기록으로 바뀌지 않는다.

양성 검사는 이 파일의 복사본에서 노출 이름 `fs__read_text_file`만 `fs-workspace__read_text_file`로 변경했다. 해당 두 호출이 P2의 `fs-workspace/tool/read_text_file` Tool ID로 연결되는지 검사했다. 총 호출 수·토큰은 유지했다. 이 입력은 매핑 경로 확인용 통제 자료이며 실제 테스트베드에서 호출한 증거가 아니다. ambiguous·동명 Tool 전체 경우는 이번 양성 검사의 범위가 아니다.

## 남은 것과 연동 판단

② 스냅샷 수용·미귀속 보존·통제 입력의 실제 ID 매핑·파일/API 비교와 ③ 저장 출력 계약 검사·빌드·화면 로딩·프록시 사용량 표시는 QA에서 실행 가능했고 이번에 통과했다. 사용자가 새 스냅샷을 만들어 배포할 필요는 없다.

실제 테스트베드 호출의 matched 검증은 해당 VM의 OTLP/결과 기록이 필요하다. 새 스냅샷보다 **선택한 P2와 같은 실제 환경의 호출 기록**이 필요한 상태다. 라이브 파일 재읽기·플러그인 실행·VM/TLS·최신 스캐너 ee9c1e0→대시보드 재생성(①)은 이번에 실행하지 않았다.

최신 대시보드는 이미 0.7 출력을 생성하며 0.6 입력을 거부한다. 이전 QA 보고서와 제출 범위 문서의 0.6 설명은 기존 실행 당시 구현 기준으로 읽고, 이번 확인 버전을 0.6으로 되돌리지 않는다. 전체 공통 0.7 계약 준수를 인증한 것은 아니다. 현재 검사기는 대시보드 작성자가 제공한 Python/브라우저 검사기이며 공식 JSON Schema 전체 검증을 대신하지 않는다.

scope 협의 메모는 gateway_identity 11·node_identity 11·agent_exposure 11·gateway_pairing 10건이다. 검사기에서 오류로 판정하지 않았으며 이번 연결을 차단하지 않았다.

빌드 첫 시도에서는 esbuild의 상위 디렉터리 접근이 샌드박스에서 거부됐다. 같은 소스에 대해 허용된 실행 환경으로 재시도해 통과했다. 소스 수정으로 우회하지 않았다.
