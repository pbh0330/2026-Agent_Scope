# QA 테스트 케이스

## 1. 공통 기록 규칙

- 실제 실행 결과는 `QA_실행결과.md`에 기록한다.
- 모든 테스트는 실행한 commit, 스키마 버전 및 기준 스냅샷을 명시한다.
- 필드·상태·수집 결과 테스트는 [공통 스키마](https://github.com/pbh0330/2026-Agent_Scope/blob/9085e8deb4820b3c7582224f3e5dbac42e28a52d/docs/schema-design-draft.md)의 0.7.0-draft를 준비 기준으로 한다. 검토 기준은 PR #18 HEAD `9085e8deb4820b3c7582224f3e5dbac42e28a52d` (2026-11-13)이며 문서 v0.7.5 / 계약 0.7.0-draft다. 8종 분류는 확정이며 세부 필드·관계·ID와 구현 지원은 별도 확인한다. 실행 전 적용 문서 버전·commit과 담당자 합의를 기록하며 미합의 세부 조건은 Blocked와 사유를 남긴다.
- 결과 판정은 `Pass`, `Fail`, `Blocked`, `N/A` 중 하나를 사용한다.
- 실행 전 상태는 `NOT_RUN`(기존 표의 `미실행`)으로 기록한다. 확인된 결함은 GitHub Issue로 관리하고 실행결과에 Issue 번호·URL을 연결한다.
- `MAY_*` 관계는 정적 근거에 따른 추론이며 실제 접근·전송 사실로 판정하지 않는다.
- 실제 토큰, API key, client secret 또는 private key는 입력·출력·증적에 남기지 않는다.

## 2. S1~S5 위협 시나리오 테스트

아래 S1~S5 테스트를 계획된 필수 검증 목록에 포함한다. 로컬 준비 자료 `위협시나리오.md` (미공유 후보; 실행 전 확정 문서 인수 필요)를 기준으로 준비하며, 실행 전 담당자와 문서 버전, 정상/위협 입력, 기대 경고·근거를 확정한다. 기존 QA-S1~QA-S5 테스트 ID를 유지하고 세부 조건을 갱신한다. 실행에 필요한 기준이나 환경이 없으면 `Blocked`와 사유를 기록한다.

구체적인 입력과 합격 조건은 수집 가능 범위와 담당자 합의에 따라 확정한다. 정적 결과만으로 권한 탈취·민감정보 접근·비인가 도구 실행 성공을 판정하지 않는다. 런타임 이벤트/로그 검증은 별도 범위·스키마 합의 후 추가한다.

### QA-S1-01 비인가 MCP 서버 등록 및 노출 탐지

| 항목 | 내용 |

| 목적 | 승인되지 않은 MCP Server가 설정에 추가되고 Agent에 노출될 가능성을 식별하는지 확인 |
| 사전 조건 | 승인된 서버만 있는 기준 스냅샷 및 승인 목록 확보 |

| 기대 관계 | 확인된 선언 주체 Gateway/Node/Plugin `DECLARES` Server, 근거가 있는 Skill/Plugin `ASSOCIATED_WITH` Server. 관계 이름·방향은 적용 계약 합의 후 판정 |
| 기대 경고 | 미승인 endpoint·출처·무결성·잠재 노출 근거를 포함한 경고 |

| 관련 회귀 | QA-COL-01, QA-REL-01, QA-SEC-01 |

| 항목 | 내용 |

## 3. 자산 수집 테스트

### QA-COL-01 8종 정점 수집

- 입력: 8종 자산이 각각 하나 이상 존재하는 테스트 환경
- 기대 결과: Gateway, Node, MCP Server, Tool, Resource/Template/Prompt, Skill, Plugin, Permission/Auth가 유형을 보존해 수집된다.
- 확인 사항: resource_prompt의 resource/resource_template/prompt, permission_auth의 permission/authentication을 asset_subtype으로 구분한다. Credential·Host·Client·Agent를 별도 아홉 번째 수집 유형으로 만들지 않는다. 미지원 유형은 정상 0건으로 처리하지 않으며 미구현 때문에 검증할 수 없는 조건은 Blocked로 기록한다.

### QA-COL-02 Gateway·Node 분산 설정 수집

- 입력: Gateway와 Node 양쪽에 서로 다른 MCP Server 선언
- 기대 결과: 두 위치의 서버가 모두 수집되고 선언 위치가 보존된다.
- 실패 조건: 한쪽 설정 전체가 누락되거나 선언 주체가 뒤바뀐다.

### QA-COL-03 안정적인 복합 식별자

- 절차: 설정 변경 없이 같은 환경을 두 번 스캔한다.
- 기대 결과: 동일 자산의 ID가 유지되고 중복 정점이 생기지 않는다.
- 추가 확인: 서로 다른 Server의 동명 Tool ID는 달라야 한다.

### QA-COL-04 필수·선택 필드 누락 처리

- 입력: 선택 필드가 없고 일부 레코드에는 필수 필드가 없는 테스트 설정
- 기대 결과: 선택 필드 누락은 안전하게 처리하고, 필수 필드 누락은 해당 항목과 원인을 명확히 보고한다.
- 실패 조건: 전체 스캔이 설명 없이 종료되거나 잘못된 기본값으로 위험을 숨긴다.

### QA-COL-05 잘못된 설정 파일 격리

- 입력: 정상 설정과 구문 오류가 있는 테스트 설정을 함께 배치
- 기대 결과: 오류 위치와 원인을 기록하며 처리 가능한 다른 자산의 결과는 보존한다.

### QA-COL-06 정상 빈 목록

- 입력: 성공적으로 완료된 `tools/list`가 빈 목록을 반환하는 구성
- 기대 결과: 해당 수집은 `success`, Tool 수는 0이며 실패와 구분된다. 전체 scan 상태는 다른 수집 작업의 결과까지 반영한다.

### QA-COL-07 목록 페이지 중간 실패

- 입력: 첫 페이지는 정상이고 다음 페이지에서 시간 초과가 발생하는 목록 응답
- 기대 결과: 확보한 자산과 근거를 보존하고 해당 작업과 전체 scan을 `partial`로 기록한다. 미수집 범위·사유를 남기고 전체 목록을 수집했다고 표시하지 않는다.

### QA-COL-08 수집 실패와 자산 삭제 구분

- 입력: 이전 스냅샷에는 Tool이 있고 현재 설정 수집은 성공하지만 Tool 목록 조회는 실패하는 구성
- 기대 결과: 현재 목록 작업은 `failed`, 전체 scan은 `partial`이다. 이전 Tool을 이번에 수집한 것처럼 복사하거나 이번 누락을 삭제로 확정하지 않는다. 대시보드는 실패 범위와 이전 스냅샷을 구분한다.

### QA-COL-09 유형별 지원·빈 결과·실패 구분

- 입력: 정상 조회 0건, 미지원 유형, 조회 실패의 세 구성과 수집 범위·지원 목록
- 기대 결과: 수집 결과와 제약에서 세 상태를 구분한다. 빈 assets 배열만으로 성공을 판정하지 않고 미지원·실패를 자산 없음이나 삭제로 표시하지 않는다.
- 판정: 이 상태 구분 테스트는 실제 표시 동작으로 판정하며, 유형별 수집 구현 완료와 별개로 기록한다.

### QA-COL-10 선언 주체와 실행 위치 분리

- 입력: Gateway에 선언되고 Node VM에서 실행되는 P2 원격 서버 및 Plugin manifest에만 등록된 서버
- 기대 결과: owner_ref는 확인된 선언 주체를 참조한다. 실행 위치는 별도 증적이 있을 때만 기록하며 URL·owner_ref로 추정하지 않는다. mcp list에 없다는 이유로 manifest 선언을 누락하지 않는다.

## 4. 관계 및 스키마 테스트

### QA-REL-01 관계 방향과 소유 주체

- 기대 결과: 합의한 관계 계약에서 `DECLARES`는 확인된 선언 주체 Gateway/Node/Plugin에서 Server로, `ADVERTISES`는 Server에서 제공 자산으로 연결된다. 선언 소속과 실제 실행 위치를 혼동하지 않는다.
- 실패 조건: 방향이 반대이거나 자산을 참조하는 출발·도착 ID가 존재하지 않는다. Agent·접근 자원·외부 목적지 등 비정점 대상은 합의된 `TargetRef` 규칙으로 검증하며 별도 수집 자산으로 집계하지 않는다.

### QA-REL-02 추론 관계의 근거와 신뢰도

- 기대 결과: `MAY_EXPOSE_TO`, `MAY_ACCESS`, `MAY_SEND_TO`에는 합의된 evidence·confidence 정보가 있다.
- 실패 조건: 정적 추론을 실제 행위로 확정하거나 근거 없이 관계를 생성한다.

### QA-SCHEMA-01 출력 스키마 유효성

- 공통 참조: context.gateway_ref는 같은 스냅샷의 Gateway 자산을 참조하고 Tool·Resource/Template/Prompt의 owner_ref는 소속 Server를 참조한다.

- 기대 결과: 모든 정점·관계가 합의된 형식, 자료형, 필수 필드 및 열거값을 만족한다.
- 확인 사항: 공식 MCP 정보와 프로젝트 확장 정보가 합의된 방식으로 구분된다.

### QA-SCHEMA-02 하위 호환성과 버전

- 입력: 이전에 저장한 정상 출력과 변경된 스키마 출력
- 구버전 검증: 0.6.0-draft 등 7종 입력을 버전 문자열만 바꿔 수용하지 않는다. 기존 QA의 Gateway 포함 7종과 Gateway 제외·Permission/Auth 포함 7종을 구분한다. 실제 identity·증적으로 Gateway를 매핑하고 Permission/Auth 보완, owner_ref·gateway_ref·TargetRef·관계·집계·Ground Truth를 함께 변환한다. 변환기 버전과 미보완 범위를 기록한다.
- 기대 결과: 스키마 버전을 식별할 수 있고, 비호환 변경은 명시적으로 실패하거나 변환 절차를 제공한다.

### QA-SCHEMA-03 상태의 미확인·부정 판정 구분

- 입력: 정책 미확인 상태와 특정 Agent에 대한 노출 금지가 확인된 상태
- 기대 결과: 미확인은 `null`과 사유 또는 생략에 따른 unknown, 확인된 부정은 `false`와 근거·대상·정책 참조로 표현한다. 정적 출력에서 `CALLABLE`·`USED`를 true/false로 확정하지 않는다.

### QA-SCHEMA-04 계약 오류 거부와 부분 수집 수용

- 입력: 중복 ID, 없는 자산·근거·수집 작업 참조, 잘못된 TargetRef를 각각 포함한 출력 및 별도의 유효한 partial 출력
- 기대 결과: 계약 오류는 위치·원인을 알리고 거부한다. 유효한 partial 출력은 수용하고 실패 범위를 표시한다.

### QA-REL-03 Permission/Auth 적용 대상과 집계

- 입력: 두 서버에 적용되는 하나의 permission 정책, 별도의 authentication 설정 및 대상 미확인 설정
- 기대 결과: assets[]의 permission_auth로 저장하고 하위 유형을 구분한다. 초안의 project.permission_auth.target_refs는 실제 대상 asset_id를 참조하며 미확인은 빈 배열과 reason으로 표현한다. 적용 대상 두 개를 정책 두 건으로 세거나 snapshot.policies에 중복 저장하지 않는다.
- 참조 확인: policy_ref는 같은 스냅샷의 permission 하위 유형 자산을 참조한다. 같은 환경변수 이름만으로 자격증명 공유를 확정하지 않는다. 적용 선언을 실제 권한 부여·인증 성공으로 표현하지 않는다.
- 사전 조건: 적용 대상 필드와 정책 집계 단위 합의. 미합의 세부 조건은 Blocked로 기록한다.

### QA-REL-04 Gateway–Node 페어링 후보

- 사전 조건: PAIRED_WITH 이름·방향·완전성 판정 규칙과 실제 원천을 합의한다.
- 입력: 페어링 증적이 있는 구성과 목록 조회 실패·부분 수집 구성
- 기대 결과: 합의 시 Gateway → Node 관계와 증적을 보존한다. 페어링을 현재 접속·호출 성공으로 표시하지 않고 조회 실패를 관계 해제·Node 삭제로 판정하지 않는다. 재페어링 전후 ID는 별도 합의한 ID 규칙으로 비교한다.

### QA-SCHEMA-05 P0 full 정답과 ID 매핑 인수

- 입력: 같은 환경·논리 프로필·스냅샷 범위의 실제 P0 InventorySnapshot 및 full GroundTruth. 차분은 합의한 추가·변경·삭제·종속 관계 규칙으로 full 목록을 생성한 뒤 사용
- 기대 결과: 정답 ID와 출력 ID를 matched/ambiguous/unmatched와 사유로 기록하고 이름만으로 매핑하지 않는다. 중복 ID·owner_ref·gateway_ref·관계·정책 대상·증적 참조를 검사하며 예시/TBD 행을 분모에 넣지 않는다.
- 확인 사항: 스키마·ID 규칙·정답 생성기·변환기 버전을 기록한다. ID 함수를 공유해도 공통 테스트 벡터와 실제 원천 증적으로 별도 검토한다.

## 5. 보안 테스트

- 확인 위치: 스캐너 출력, 오류 로그, 디버그 로그, 대시보드, 다운로드 파일
- 기대 결과: 존재 여부, 유형 또는 비식별 참조만 표시된다.

### QA-SEC-02 악성·비정상 광고 응답 내성

- 입력: 합의된 처리 한도를 초과하는 description, 예상하지 못한 필드, 잘못된 자료형을 반환하는 테스트 Server
- 기대 결과: 한도 초과·유효하지 않은 응답은 오류를 격리하고 보고한다. 허용된 확장 필드는 계약에 따라 처리하며 무조건 오류로 판정하지 않는다. 정상 빈 목록은 QA-COL-06으로 검증한다.

## PR #18 반영 기준 (2026-11-13)

- 검토 기준: [PR #18 공통 스키마](https://github.com/pbh0330/2026-Agent_Scope/blob/9085e8deb4820b3c7582224f3e5dbac42e28a52d/docs/schema-design-draft.md) HEAD `9085e8deb4820b3c7582224f3e5dbac42e28a52d`. 문서 개정 v0.7.5와 데이터 계약 `0.7.0-draft`를 구분한다. 기존 PR #1은 8종 분류의 근거로 유지한다. 이 기준은 최종 계약 합의나 구현 완료를 뜻하지 않는다.
- 첫 실행은 최신 스캐너 → #13 기존 어댑터 → 대시보드의 실제 P0 한 건으로 진행한다. 선택한 스냅샷의 환경·프로필·자산 ID를 공유하고 Gateway 참조를 실제 Gateway asset_id에 연결한다. 최종 ID·Permission 전체 합의는 첫 연결의 선행 조건이 아니다. 미합의 조건만 Blocked로 분리한다.
- 검토 fixture는 원천 자산 17개·관계 16개의 변환 예제다. 임시 ID와 가상 시각을 실제 실행 증적으로 사용하지 않는다. #13의 20개 자산은 정책/인증 3개를 별도 대조한다. 관계 18개는 APPLIES_TO 3개 추가·PAIRED_WITH 제외의 차이를 확인한다. 근거 없는 페어링을 만들거나 정책 자산을 개수에 맞춰 제거하지 않는다. APPLIES_TO는 구현 관계로 구분한다.
- 정상 0건·영역 미선언·미지원·조회 실패·partial을 구분한다. fixture의 partial은 가져온 인증 맥락·페이지 완전성 정보 부족이며 실제 조회 실패가 아니다. 실제 상태는 수집 계획·결과로 계산한다. 범위 밖 작업 미수행을 실패로 집계하지 않는다.
- 두 MCP 버전 처리·선언값 수집과 기존 어댑터·정적 탐지·사용량 API는 구현된 경로를 먼저 검증한다. 담당자 테스트 보고와 QA 독립 실행을 구분한다. 스캐너 712개는 테스트 수집 수이며 전체 실행 통과 수가 아니다.

## 9. 첫 연동 추가 테스트

### QA-INT-01 실제 P0 수집·변환·화면 일치

- 입력: 동일 환경·프로필의 실제 P0 스캐너 출력, #13 기존 어댑터 출력, 원천 full 정답 및 정책/인증 추가 자산의 근거.
- 절차: 실행 commit·스냅샷을 고정하고 원천→변환→화면의 ID 매핑, owner_ref·gateway_ref·증적 참조와 관계 방향을 대조한다.
- 합격: gateway_ref는 동일 스냅샷의 Gateway asset_id다. 원천 17개와 추가 정책/인증을 나눠 비교하고 범위별 누락·오탐을 기록한다. 동명 Tool을 이름만으로 합치지 않는다. 실제 페어링 근거가 없으면 생성하지 않고 정답과 차이를 기록한다.
- 부정 입력: 없는 Gateway 참조는 QA-SCHEMA-04에 따라 원인을 표시하고 거부한다. 유효 partial은 수용하고 불완전 범위를 표시한다. 실제 P0가 없으면 Blocked이며 fixture로 대체 통과하지 않는다.

### QA-INT-02 최신 스캐너 필드 보존

- 입력: sslVerify true/false/누락, toolFilter include/exclude/누락, Node 영역·Plugin manifest 선언과 실제 조회 결과를 가진 통제 입력.
- 절차: 원천과 어댑터 결과를 비교하고 과거 보강·버전 우회 경로의 적용 조건을 확인한다.
- 합격: 명시적 false와 누락을 구분하고 선언값을 보존한다. 예전 보강값이 최신 수집값을 덮어쓰지 않는다. 확인된 선언 주체와 실행 위치를 구분하며 선언 Server와 조회 Tool이 올바르게 연결된다.
- 회귀: MCP 2025-11-25·2026-07-28의 저장 응답을 각각 처리하고 실제 P0 협상 버전은 별도 실측한다. 필터 일치만으로 EXPOSED/CALLABLE을 확정하지 않는다.

## 10. 사용량 파일/API 통합 테스트

### QA-USAGE-01 자산 매핑과 동명 Tool

- 입력: 같은 Tool 이름을 가진 두 Server, Gateway/Node 노출 이름, 후보 1개·복수·없음, 인벤토리 없음.
- 합격: 서버 원천 키·소속·원래 Tool 이름과 실제 어댑터 ID로 연결한다. 유일 후보는 matched, 복수는 ambiguous, 후보/스냅샷 없음은 unmatched다. 이름만으로 임의 연결하지 않고 미귀속도 호출 수·관측 근거와 함께 보존한다.

### QA-USAGE-02 환경·프로필과 버전 불일치

- 입력: 선택 스냅샷과 환경 또는 프로필이 다른 실행 인자, 0.6 출력과 0.7 계약 소비자.
- 합격: 환경·프로필 불일치는 이유와 함께 거부한다. 버전 문자열만 바꿔 수용하지 않고 명시적 변환·참조·집계 검토 또는 비호환 거부를 기록한다. review용 식별자를 실환경 값으로 복사하지 않는다.

### QA-USAGE-03 파일·API·화면 집계

- 입력: matched/ambiguous/unmatched, 계산 불가 null, 정상 0을 포함한 usage.json과 같은 데이터의 API 응답. 동일 조회 구간·필터·페이지 전체를 사용한다.
- 합격: 파일과 API는 각 형식의 의미를 대조하며 자산 ID·호출 수·사용량 합계가 일치한다. 화면에서 null을 0으로 바꾸거나 미귀속을 누락하지 않는다. 추정 배분은 계산 방식·버전·근거를 표시한다.

### QA-USAGE-04 병렬·배치 배분 경계

- 입력: 완전한 결과별 토큰 수·구간 증가분, 일부 결과 누락, 음수 증가분, 결과별 토큰 합 0 및 고정분 총합이 구간 증가분을 넘는 경계 입력.
- 합격: 합의된 k·배분 버전·반올림/허용 오차에서 완전한 구간의 배분 합이 보존된다. 일부 결과/블록 미확보와 unattributed는 null이며 임의 0·음수 배분을 만들지 않는다. 음수 보정은 negative_delta로 구분한다.
- 사전 조건: k, 경계 처리와 허용 오차를 토큰 담당자와 확정한다. 미합의 경계 조건만 Blocked로 기록하고 나머지 매핑·표시 검증은 진행한다.
