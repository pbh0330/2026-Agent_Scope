# QA 문서 안내

## 목적

AI Agent 자산 식별 및 보안 가시화 시스템의 기능과 분석 결과를 검증한다.

이 폴더는 MCP 기반 AI 에이전트 자산 스캐너와 그래프 대시보드의 품질 검증 자료를 관리한다.

## 시나리오 기준 및 담당

위협 시나리오 작성·확정은 시나리오/대시보드 담당 파트에서 수행하고, QA는 전달받은 기준을 테스트와 정답 데이터로 구체화한다. 현재 QA는 S1~S5의 5개 시나리오를 진행 기준으로 삼으며, 세부 입력과 기대 조건은 담당자와 확정한다.

참고 자료는 [위협 시나리오 후보](../위협시나리오.md)의 S1 비인가 서버, S2 과도한 권한 Tool, S3 동명 Tool 충돌, S4 자격증명 공유, S5 안전하지 않은 연결이다. 문서의 후보 내용을 기준으로 테스트를 준비하되 실행 시 적용한 문서 버전과 합의된 기대 조건을 기록한다.

S1~S5 관련 테스트를 계획된 필수 검증 목록에 포함한다. 담당자로부터 확정 문서 위치·ID·버전, 정상/위협 구성, 기대 경고·근거 및 제공 데이터를 받아 관련 테스트와 Ground Truth를 구체화한다. 실행에 필요한 기준이나 환경이 없으면 `Blocked`와 사유를 기록한다. 공통 자산·관계·스키마·보안 테스트는 자체 사전 조건을 충족하면 진행할 수 있다.

런타임 이벤트/로그 검증은 데이터 스키마와 제공 방식, QA 범위를 합의한 뒤 추가한다. 정적 결과만으로 실제 민감정보 접근이나 비인가 도구 실행 성공을 판정하지 않는다.

## QA 산출물

- **Test Cases**: 테스트 입력, 절차 및 기대 결과 — `QA_테스트케이스.md`
- **Ground Truth**: 비교 기준이 되는 정답 자산·관계·경고 — `QA_GroundTruth.md`
- 테스트베드 정답 JSON 인수 후에는 파일 경로·commit을 고정하고, `QA_GroundTruth.md`에 검토 결과·ID 매핑·조건별 증적을 연결한다. PR 초안의 예시는 실제 정답으로 집계하지 않는다.
- **Test Results**: 실제 결과, 기대 결과와의 비교 및 판정 — `QA_실행결과.md`
- **Defect Reports**: 재현 절차, 영향, 담당자, 수정 및 재검증 기록 — GitHub Issues
- **Evidence**: 비밀값을 제거한 설정, 스캐너 출력, 로그, 화면 캡처. 증적 ID와 파일 경로 또는 URL을 Ground Truth 및 실행결과에 기록한다.

## 기본 작업 순서

1. 담당자가 확정한 위협 시나리오와 공통 출력 스키마를 전달받아 합격 조건을 정한다.
2. 기준 스냅샷을 확보하고 `QA_GroundTruth.md`에 정답 데이터를 기록한다.
3. `QA_테스트케이스.md`의 테스트를 실행한다.
4. 결과와 증적을 `QA_실행결과.md`에 남긴다.
5. 기대 결과와 실제 결과를 비교해 판정한다.
6. 확인된 결함은 GitHub Issue로 등록하고 실행결과에 Issue 번호와 링크를 연결한다.
7. 수정본을 재검증하고 관련 회귀 테스트 및 `develop` 반영 확인 후 Issue를 종료한다.

Test Scenario → Ground Truth 작성 → Test Case 수행 → Actual Result 기록 → Expected/Actual 비교 → Defect Issue 등록 → 수정 → Regression Test

## 판정 원칙

- **Pass**: 기대 결과를 모두 충족하고 차단 수준의 부작용이 없다.
- **Fail**: 기대 결과와 다르거나 보안·데이터 무결성 문제가 있다.
- **Blocked**: 환경, 미구현 기능 또는 외부 의존성 때문에 실행할 수 없다.
- **NOT_RUN**: 아직 테스트를 실행하지 않았다. 기존 실행결과의 `미실행`과 같은 상태이며 실패나 실행 불가 판정이 아니다.
- **N/A**: 합의된 현재 범위에 적용되지 않는다.

`PASS`/`FAIL`/`BLOCKED`는 기존 문서의 `Pass`/`Fail`/`Blocked`와 같은 의미다. 테스트 판정과 Issue의 처리 상태는 별도로 관리한다.

## 결함 심각도 및 GitHub Issue 관리

기존 QA 기준과 일치하도록 다음 4단계를 사용한다.

| 심각도 | 기준 |
|---|---|
| Critical | 비밀값 노출, 결과 전체 손상 또는 검증 불가능 |
| High | 핵심 시나리오 탐지 실패 또는 주요 자산·관계 누락 |
| Medium | 일부 기능 오류지만 우회 또는 수동 확인 가능 |
| Low | 기능 영향이 작은 표현·사용성 문제 |

**운영은 GitHub Issues, 보고는 QA 실행결과 문서**로 분리한다. 결함의 담당자·최신 상태·수정 PR·재검증 이력은 Issue에서 관리한다. 실행결과에는 실행 시점의 판정, 통과·실패 수, 측정 지표, 잔여 위험 및 Issue 링크를 기록한다. Issue가 해결되어도 과거 결과를 덮어쓰지 않고 재검증 기록을 추가한다.

[QA 결함 보고 Issue Form](../.github/ISSUE_TEMPLATE/qa-defect.yml)은 TC ID / Expected / Actual / Severity / 재현 절차 / Evidence / Environment를 필수로 받는다. 상세 작성 및 종료 기준은 [결함 관리 안내](QA_결함관리.md)를 따른다.

GitHub 업로드 시 `QA/`와 함께 `.github/ISSUE_TEMPLATE/qa-defect.yml`을 대상 저장소 루트 기준으로 배치하고 기본 브랜치에 반영한다. 필수 입력 검사는 이 폼으로 제출할 때 적용되며, 내용의 정확성이나 비밀값 포함 여부를 자동 검증하지 않는다.

## GitHub 업로드 전 민감정보 점검

문서, 정답 데이터, 로그, 화면 캡처와 Issue/PR 본문·첨부파일 모두 공개 전에 점검한다. 아래 항목은 수동 점검 기준이며 자동 필터가 적용된다는 의미는 아니다.

- [ ] 실제 API key, token, password, client secret, private key, 인증 Header, 세션 Cookie가 없다. 실제 비밀값은 전체를 제거하고 `<REDACTED>` 또는 참조 이름으로 대체한다.
- [ ] 실제 계정·이메일, 내부 IP·호스트명, 민감한 endpoint 및 사용자명이 포함된 로컬 경로를 확인하고 불필요한 식별정보는 `<TB_USER>`, `<TB_GW_IP>` 등의 자리표시자로 치환했다.
- [ ] `.env`, 자격증명 파일, 원본 설정·로그, 백업·압축파일이 업로드 대상에 섞이지 않았다.
- [ ] 화면 캡처의 주소창·터미널·배경 창까지 확인하고, 가린 값이 복원되지 않도록 정제된 이미지로 내보냈다.
- [ ] 정제 후에도 테스트 ID, 관계 참조 및 재현에 필요한 구조를 유지하고, 실제 업로드할 파일과 commit 변경 내용을 다시 확인했다.

민감정보가 발견되면 원본을 Issue에 붙이지 않고 정제본만 공유한다. 이미 commit된 비밀값은 현재 파일에서 지우는 것만으로 과거 이력에서 없어지지 않는다. 노출된 자격증명은 폐기·교체하고 이력 처리 후 공유한다.

테스트 결과에는 설정 파일, 스캐너 출력, 로그 또는 화면 캡처 중 하나 이상의 재현 증적을 첨부한다. 토큰, API key, secret 등 실제 비밀값은 문서와 증적에 기록하지 않는다.
