# Agent Scope

AI 에이전트 보안을 위한 자산 식별 및 가시화 기술 개발 프로젝트입니다.

본 저장소는 `main`과 `develop`을 기준으로 작업을 통합하며, 기능
개발·수정·문서 작성 등의 개별 작업은 작업 단위 브랜치에서 진행합니다.

------------------------------------------------------------------------

## Git Branch Strategy

### 기본 브랜치

  브랜치        용도
  ------------- ----------------------------------------------
  `main`        검증이 완료된 안정적인 결과
  `develop`     개발 중인 작업을 통합하는 브랜치
  작업 브랜치   기능 개발, 수정, 문서 작성 등 개별 작업 수행

`main`과 `develop`에는 직접 push하지 않습니다.

모든 변경사항은 작업 브랜치에서 작업한 뒤 Pull Request를 통해
병합합니다.

------------------------------------------------------------------------

## 작업 브랜치 명명 규칙

작업 브랜치는 다음 형식을 사용합니다.

``` text
<type>/<작업명>
```

예시:

``` text
feature/asset-scanner
feature/dashboard
feature/threat-scenario
feature/token-collector
feature/testbed

fix/scanner-path
docs/threat-scenarios
refactor/asset-schema
test/scanner-collection
chore/project-setup
```

### Type

  Type         용도                        예시
  ------------ --------------------------- ---------------------------
  `feature`    새로운 기능 개발            `feature/asset-scanner`
  `fix`        버그 수정                   `fix/scanner-path`
  `refactor`   동작 변경 없는 코드 개선    `refactor/asset-schema`
  `docs`       문서 작성 및 수정           `docs/threat-scenarios`
  `test`       테스트 추가 및 수정         `test/scanner-collection`
  `chore`      설정, 의존성 등 기타 작업   `chore/project-setup`

### 브랜치 작성 원칙

-   영문 소문자와 숫자를 사용합니다.
-   단어 사이는 하이픈(`-`)으로 구분합니다.
-   공백, 한글, 밑줄(`_`)은 사용하지 않습니다.
-   담당자별 고정 브랜치가 아니라 **작업 단위 브랜치**를 생성합니다.
-   하나의 브랜치에서는 가급적 하나의 Issue 또는 하나의 명확한 작업만
    진행합니다.
-   작업 내용을 알 수 있도록 짧고 구체적인 이름을 사용합니다.
-   다른 팀원의 작업 브랜치에서 임의로 새 브랜치를 만들지 않습니다.
-   아직 병합되지 않은 다른 작업에 의존해야 한다면 먼저 팀과 조율합니다.

------------------------------------------------------------------------

## 개발 흐름

기본 작업 흐름은 다음과 같습니다.

``` text
Issue 생성
    ↓
최신 develop에서 작업 브랜치 생성
    ↓
구현 및 테스트
    ↓
Pull Request 생성
    ↓
팀원 1명 이상 승인
    ↓
develop에 병합
    ↓
Issue 확인 및 종료
```

작은 문서 수정이나 단순 오타 수정처럼 별도의 추적이 필요하지 않은 작업은
Issue 생성을 생략할 수 있습니다.

------------------------------------------------------------------------

## 1. Issue 생성

독립적인 개발 작업을 시작하기 전에 Issue를 생성합니다.

Issue에는 가능한 한 다음 내용을 작성합니다.

-   작업 배경 및 목적
-   구현 범위
-   완료 조건
-   담당자

하나의 Issue는 하나의 명확한 작업 단위로 작성하는 것을 원칙으로 합니다.

------------------------------------------------------------------------

## 2. 최신 develop에서 작업 브랜치 생성

일반 작업 브랜치는 반드시 최신 `develop`을 기준으로 생성합니다.

``` bash
git fetch origin
git switch develop
git pull --ff-only origin develop
git switch -c feature/asset-scanner
```

다음 방식은 사용하지 않습니다.

-   `main`에서 일반 작업 브랜치를 직접 생성
-   다른 팀원의 작업 브랜치에서 임의로 분기
-   오래된 로컬 `develop`에서 새 작업 브랜치 생성

------------------------------------------------------------------------

## 3. 구현 및 Push

Issue 또는 작업 범위에 해당하는 내용을 구현합니다.

최초 push 시:

``` bash
git push -u origin feature/asset-scanner
```

이후에는 다음과 같이 push할 수 있습니다.

``` bash
git push
```

가능하면 Pull Request를 생성하기 전에 로컬에서 해당 기능과 관련 테스트를
확인합니다.

------------------------------------------------------------------------

## 4. Pull Request 생성

작업이 완료되면 작업 브랜치에서 `develop`을 대상으로 Pull Request를
생성합니다.

``` text
base: develop
compare: 작업 브랜치
```

PR에는 최소한 다음 내용을 기록합니다.

-   관련 Issue 번호
-   주요 변경 내용
-   확인 또는 테스트 방법
-   리뷰 시 확인이 필요한 사항

예시:

``` text
Related to #12
```

------------------------------------------------------------------------

## 5. Pull Request 리뷰

모든 Pull Request는 작성자를 제외한 **팀원 1명 이상**의 승인 리뷰를 받은
뒤 병합합니다.

리뷰어는 다음 내용을 중심으로 확인합니다.

-   작업 요구사항을 충족했는가
-   기존 기능에 영향을 주는 문제가 없는가
-   오류 가능성이 없는가
-   필요한 테스트가 수행되었는가

`Request changes`가 등록된 경우 해당 내용을 반영한 뒤 다시 리뷰를
요청합니다.

### 공통 스키마 및 인터페이스 변경

다른 팀원의 작업에 영향을 주는 다음과 같은 변경은 관련 담당자와 반드시
확인합니다.

-   공통 데이터 스키마
-   API 요청·응답 형식
-   스캐너 출력 형식
-   대시보드 입력 형식
-   모듈 간 인터페이스

------------------------------------------------------------------------

## 6. develop에 병합

리뷰와 확인이 완료되면 작업 브랜치를 `develop`에 병합합니다.

기본 병합 방식은 다음과 같습니다.

``` text
Squash and merge
```

병합 후 사용이 끝난 작업 브랜치는 삭제합니다.

------------------------------------------------------------------------

## 7. Issue 종료

`develop`에 병합된 결과를 확인한 뒤 관련 Issue를 종료합니다.

필요한 경우 Issue에 다음 내용을 남깁니다.

-   관련 PR 번호
-   구현 결과
-   테스트 또는 확인 결과
-   후속 작업 여부

Issue 자동 종료 여부에 의존하기보다 실제 `develop` 반영 결과를 확인한 뒤
종료하는 것을 원칙으로 합니다.

------------------------------------------------------------------------

## main 반영

일정 단위의 개발 결과가 충분히 검증되면 `develop`에서 `main`을 대상으로
Pull Request를 생성합니다.

``` text
base: main
compare: develop
```

이 PR 역시 작성자를 제외한 팀원 1명 이상의 승인 리뷰를 받은 뒤
병합합니다.

------------------------------------------------------------------------

## 브랜치 구조 예시

``` text
main
 │
 └── develop
      │
      ├── feature/asset-scanner
      ├── feature/dashboard
      ├── feature/threat-scenario
      ├── feature/token-collector
      ├── feature/testbed
      ├── fix/scanner-path
      └── docs/threat-scenarios
```

------------------------------------------------------------------------

## 핵심 규칙

1.  `main`, `develop`에 직접 push하지 않습니다.
2.  모든 작업 브랜치는 최신 `develop`에서 생성합니다.
3.  담당자별 고정 브랜치가 아닌 **작업 단위 브랜치**를 사용합니다.
4.  한 브랜치에서는 하나의 명확한 작업을 진행합니다.
5.  작업 완료 후 `develop`을 대상으로 Pull Request를 생성합니다.
6.  Pull Request는 작성자를 제외한 팀원 1명 이상의 승인 후 병합합니다.
7.  공통 스키마나 인터페이스 변경은 영향을 받는 담당자와 확인합니다.
8.  기본적으로 `Squash and merge`를 사용합니다.
9.  병합이 끝난 작업 브랜치는 삭제합니다.
10. 검증된 개발 결과는 `develop`에서 `main`으로 Pull Request를 통해
    반영합니다.

이 규칙은 Git 사용 자체를 복잡하게 만드는 것이 아니라, 팀원 간 작업
충돌을 줄이고 변경사항과 리뷰 이력을 명확하게 관리하는 것을 목적으로
합니다.
